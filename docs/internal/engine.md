Binding notes for the `engine` module. Contract: `docs/contract/endpoints.md` "Scoring engine data", `jobs.md` (`engineEndings`). Request and DOM's plan: `docs/requests/CR-056-scoring-engine.md`. Test IDs: EN-*.

## Release plan
- **5.4.0 (data, built):** `POST /engine/sales`, `POST /engine/unsold`, `GET /engine/health` (data counts, endings fill), the daily `engineEndings` step.
- **5.5.0 (model, built):** features (all point-in-time), the TypeScript models (gradient boosting, logistic regression for reasons, price tier), `POST /engine/train`, `GET /engine/train/{id}`, `POST /score`, `engine_models`, the weekly `engineTrain` step; `model_version` and the model fields in `/engine/health`. ## Module
`src/modules/engine/`: `uploads.ts` (row checks, duplicate rules, the transaction), `endings.ts` (`EndingsJob`, `endingsHealth`, and since 5.5.0 the shared `askRdap` / `saveAnswer` / `endingBase` that `/score` also uses), `health.ts` (`engineHealth`), `api/engine.ts` (`registerEngine`), `index.ts`. 5.5.0 adds `features.ts` (pure, point-in-time), `data.ts` (database loaders), `dataset.ts` (rows, split, frozen hash), `train.ts` (`EngineTrainer`), `score.ts` (`Scorer`), `reasons.ts`, and `model/` (`gbm.ts`, `logit.ts`, `metrics.ts`, `rng.ts`: pure, deterministic, no dependency). It uses selection's `rdapBaseFor` and `hostPacer` (the shared per-host pacer: 4 in flight, 250 ms between starts) and `RDAP_FALLBACK_BASES` (.co, .io) from `core/rdap.ts`.

## Endings fill rules
- Pairs = every distinct name of `engine_sales` and `engine_unsold` x 6 endings (5.5.0: the five others and the name's own `.com`, asked at Verisign; the `.com` host is shared with `.net` in the host pacer, so the two together run at 4 asks a second, about 4,800 asks per 20-minute night: 32,000 names need 64,000 Verisign asks, about 13 nights for a first full fill, against about 7 before .com was added; the other registries finish earlier). Due = never asked, or unanswered and older than 6 hours, or answered more than 30 days ago. Order: never asked first, then oldest `checked_at`. A run asks at most 20,000 pairs and stops at 20 minutes (`ENDINGS_*` constants).
- RDAP only, never DNS. 404 (an RDAP-shaped body) = not registered; 200 = registered, with `created_at` from the RDAP "registration" event; timeout, 5xx, 429 or a refusal = unanswered with a reason code (`TIMEOUT`, `SOURCE_ERROR`, `RATE_LIMITED`). One retry after a 429 whose Retry-After is at most 10 s. A refusal slows the host pacer; five in a row open its breaker and the run stops asking that host.
- Writes: never asked -> insert. Unanswered row asked again -> update that row in place (it holds no answer). Answered row asked again after 30 days -> when the new answer says the same (same `registered`, same registry creation date) the row is updated in place (`checked_at`, `http_status`, `evidence`, `registrar`; 5.14.0, EN-74), otherwise a new row is inserted for the new answer; an unanswered re-ask leaves the old answer untouched. The 5.14.0 migration deleted older rows of consecutive identical answers (a row an `owned_ending_events` row points to stays; EN-75). The job's due count and pick are one statement (window count before the limit), and `endingsHealth` is one statement. No `rdap_lookups` / `screening_evidence` rows are written (about 160,000 asks would be too large for the free plan).

## Point-in-time rules (for parts 2 and 3)
- A feature `net_pit` for a row with `as_of` is true when the newest `engine_endings` row for (name, net) with `checked_at` at any time has `registered` and `created_at_registry` strictly before `as_of`. A registry only shows today's state: a name registered and dropped before the check is invisible, and a creation date after a drop-and-re-register is the new one. That is the accepted bias of the RDAP-only method (no Wayback, no DNS).
- `registered = false` or unanswered gives 0 / null for that ending; training treats unanswered as missing, not as 0.
- Word-trend features use only sales rows with `sale_date` before `as_of`; the test file is the newest full quarter and is frozen with a sha256 before training.
- Part 2 adds `engine_models` (parameters, split hash, metrics, feature list) and reads these tables; part 3 adds drift and the bars. Neither changes the tables above except by new columns or tables (5.5.0 widened `engine_endings.tld` with `com`).

## Features (5.5.0, `features.ts`)
Computed for a name and an `as_of` day: a sold row = its `sale_date`, an unsold row = its `observation_date`, a score = the request's `as_of` or today. Nothing dated on or after `as_of` is read.

| Feature(s) | Definition | Point-in-time note |
|---|---|---|
| `len`, `n_words`, `has_digit`, `has_hyphen`, `vowel_share`, `plural_end`, `one_word` | shape of the name; words = the frozen `bt1@v3` split (`splitV2`) | timeless; `n_words`, `one_word` are null when the name has no reading (digits, hyphens, unknown pieces) |
| `all_known`, `known_share`, `seg_cost_per_char` | reading found; share of the name covered by the longest readable prefix (`splitUnread`); (sum of piece costs + piece_cost per piece) / length | timeless |
| `zipf_min/mean/max` | **a SCOWL-level proxy for Zipf; wordfreq not used (no new external data).** `8 - cost/8`, clamped to 0..8, per piece (cost 8 curated -> 7, 10 -> 6.75, 22 -> 5.25, 40 -> 3, 60 city -> 0.5) | timeless (the table is frozen) |
| `trend_pit_max/min` | per word of the name: share of all `engine_sales` rows with `sale_date` in `[as_of - 365 d, as_of)` whose split holds the word; max / min over the words; null when the window holds no sale | strict: a sale on `as_of` or later never counts; the window start day counts |
| `tok_rate_pit` | mean over the words of `(sales + 1) / (sales + unsold + 2)` counted before `as_of` (sales rows; `dropped_after_held` rows) | strict `<`. **Switched off (null, left out of the model) until the dropped rows span 90 days**: before that the unsold side is all one batch date, so the rate would separate the classes by upload date alone |
| `net_pit`, `co_pit`, `org_pit`, `io_pit`, `ai_pit` | 1 if the newest `engine_endings` row says registered with `created_at_registry < as_of`; 0 if not registered, or registered on/after `as_of`; null if unanswered or registered without a creation date | RDAP shows today's state only (accepted bias, see above) |
| `n_endings_pit` | sum of the known ones; null when all five are unknown | |
| `acq_handreg`, `acq_aftermarket_or_old`, `acq_created_after`, `com_age_years` (text `acq` in /score) | the name's own `.com` creation date vs `as_of`: `handreg` when created <= 36 months (30.4375-day months) before, `aftermarket_or_old` when older, `created_after` when created on or after `as_of` (re-registered after a drop) | null when the .com is not registered or unanswered. **Model rule:** these four enter the model only if the .com date is known for at least 30% of the training unsold rows; otherwise the missingness alone gives the label away (a dropped name has no registry record, a sold one always has) and they are listed in `feature_list.excluded` |
| `demand` | newest `keyword_demand` row for the words joined with spaces from an upload whose `month` (else upload month) is <= the `as_of` month; searches, null when none | upload month <= as_of month |
| `in_regime` (not a model column) | letters only, 6..20 characters, 2..3 words in the split | |

The split table is extended at each training with the single-word terms of the current `regime` and `tech` selection lists (cost 8, like the curated class; a word already in the table keeps its cost); the terms used are stored in `params.extra_terms` so scoring reads names the same way.

## Models (5.5.0, `model/`)
- **Gradient boosting** (`gbm.ts`): histogram, up to 255 quantile bins per feature on the training rows, a separate bin for missing; leaf-wise (best gain first) to `max_leaf_nodes` 15, `min_samples_leaf` 20, learning rate 0.1, up to 300 iterations, L2 0; every split learns a default direction for missing values (gain tried both ways; the larger side when training had none); early stopping on a seeded 10% slice of the training rows, patience 20 (the model keeps the best iteration; it is not refit on the slice); sample weights; JSON model = bin edges + trees (parallel arrays with raw thresholds). Binary log-loss; the same code with K trees per iteration gives the 4-class softmax (price tier, 150 iterations, patience 15). Deterministic: only the validation slice is random and it uses the seed. It gives the event loop a turn after every iteration.
- **Logistic regression** (`logit.ts`): L2 lambda 1 on standardised features, Newton / IRLS (convex), mean imputation plus a 0/1 missing column for each feature that had missing training values. `reasons` = coefficient x standardised value per feature (plus its missing term), the top 3..5 (at least 0.05 in size when there are 3 such), `+` toward sold.
- **Metrics** (`metrics.ts`): AUC by ranks (ties half), 95% interval from a seeded 1,000-resample bootstrap; precision at the top 1% and 5% (at least one row, ties in input order) with Wilson 95%; precision at the top 1% of the test file re-weighted to one sold per 100 unsold (each unsold counts `100 * sold / unsold`, the top 1% by weight); 101 score quantiles per class on the test file for the percentiles in /score.

## Training (5.5.0, `dataset.ts`, `train.ts`)
- **Rows:** sold = `engine_sales` (.com), price >= $100, in the regime; unsold = `engine_unsold` `dropped_after_held`, `caught_by_catcher` not true, in the regime. `registered_unsold` is counted (`dataset.registered_unsold_not_used`) but not trained on in v1.
- **Split:** test = sold rows of the newest *full* calendar quarter (ended before today, IDT) with a sale; train = sold rows before it (rows after it are not used). Unsold: if the dropped rows span >= 90 days and the quarter holds some, test = observed in the quarter, train = earlier (`unsold_mode: dated`); otherwise `hash`: sha256(`seed:domain`) < 20% goes to the test file. The test file keeps at most 3 unsold per sale (deterministic hash order; all when fewer); training keeps at most 10 unsold per sold row. **Frozen:** sha256 of the sorted `domain|label|as_of` lines is written to `engine_models` before anything is fitted. Needs 20 rows per class to train and 5 per class to test, else the run fails `NOT_ENOUGH_DATA`.
- **Weighting:** one unweighted GBM and one weighted by `0.5^(age/365.25 d)` (age against the newest training row; weights rescaled per class so the class balance is unchanged). The weighted one is kept only if its test AUC >= unweighted + 0.01 (`RECENCY_MIN_GAIN`). Both AUCs are stored.
- **Queue:** `POST /engine/train` takes the `engine_train` lock, reaps stale `running` rows (45 minutes), checks 24 hours (non-failed runs), inserts the `engine_models` row (`running`), enqueues queue job `train` with `params {train_id}` (step `trainModel`, 30-minute step timeout, 25-minute training budget checked after every tree: `TRAIN_TIME_BUDGET`) and answers 202. The job lock `job:train` allows one training at a time. A failure is stored on the row and the step fails. After a success, `params` / `test_rows` of models older than the newest four are cleared.
- **Weekly:** daily step `engineTrain` (`EngineTrainer.weekly`): a running training -> skip; no model: needs rows in both tables, and a failed last run waits for a newer sales upload; with a model: needs a sales upload newer than it and (Monday in Asia/Jerusalem or the model >= 7 days old); then `start('engine-weekly')`, whose 24-hour rule can still skip.
- **Active model** = the newest `done` row. `Scorer` keeps its parsed parameters and the token index (rebuilt when the sales / unsold counts or max ids change) in memory.

## Score (5.5.0, `score.ts`)
5.14.0: the token-index cache key is the active model id plus `max(engine_uploads.id)` (one cheap read per call, no `count(*)` of the upload tables); the cache is still filled by the first `/score` after an upload or a training (no warm-up step). `loadUnsold` reads dropped-after-held rows only; `countRegisteredUnsold` gives the number of registered-unsold rows for the dataset counts. Training and the drift report give the event loop a turn every 2,000 rows (`YIELD_EVERY_ROWS`); the drift report computes each `(domain, as_of)` once and still reports every dropped row (no cap, so its numbers are unchanged).
READ-only POST (`READ_ONLY_POSTS` in `src/http/methods.ts`, matched on the routed pattern: scope READ, no idempotency, no audit). Per name: features at `as_of`, GBM probability, percentiles from the stored test quantiles, tier probabilities, logistic reasons, likely buyers (other endings registered before `as_of` with a known creation date; `live_business` from the newest `sibling_scans` row of the name when its siblings list has that host). Missing endings (no row, or unanswered) are asked live: per registry in parallel, 4 in flight, the shared host pacer, one lookup bounded by the time left, total budget 4 s (`SCORE_LIVE_BUDGET_MS`); every answer, including an unanswered one, is saved with `saveAnswer`; what was not asked in time stays null.

## Health report (5.6.0, `drift.ts`, `health.ts`)
- **Drift** is computed at the end of each training (`computeDrift` over every stored sale and every `dropped_after_held` row not caught by a catcher; the regime filter is not applied, so it shows the data as uploaded) and stored in `engine_models.metrics.drift`; health reads the active model's copy. **No model, no drift (null): there is no on-demand computation** (it needs every row's features, too heavy for a GET). Periods: each year present in the sold data and `last_quarter` (newest full quarter with a sale). Each row's features are as of its own date (`computeFeatures`), so a later `.net` never counts (EN-80). `handreg_share` is null when the .com date is known for under 30% of the period's rows. Medians of an even count are the mean of the two middle values (prices rounded to a cent).
- **Ablation:** after the weighting choice, the same GBM (same seed tag, same chosen weights, same frozen split) is refitted without `*_pit` ending columns and `n_endings_pit`; stored as `metrics.ablation {auc_without_endings, auc95, delta, p_top1_at_1pct_base, removed, features_kept}`. `delta` = full AUC minus AUC without. Null when the model holds no ending feature.
- **Bars** (`computeBars`): 1 and 5 never measured (Gavriel's checks); 2 from the table counts; 3 from the active model's test metrics (fails when the test file has fewer than 3 unsold per sale); 4 from the ablation (delta <= 0.05); 6 AUC >= 0.850 (0.809 shown as the trend reference; indicative). Thresholds are constants in `health.ts`.

## Owned-name endings watch (5.7.0, CR-058, `endings.ts`)
- **Owned names** = `domains` rows with status `owned`, `listed` or `delisted` (a `.com`; read by SQL, no import from buying or reporting). Their five endings (not `.com`) are due when never asked, when the newest answer is older than 7 days (`OWNED_RECHECK_DAYS`), or when unanswered for 6 hours. `EndingsJob.runOnce` picks them first (`ownedDue`), the bulk pick leaves their pairs out (the 30-day rule does not apply to them), and `due` counts both. Each pair carries `owned {domain, buyDate}`.
- **Events** (`recordOwnedEvent`, table `owned_ending_events`, append-only, trigger `reject_mutation`): written after the pair's answer is saved, never for an unanswered (null) answer. No earlier event: `baseline`, or `newly_registered` when registered with a creation date whose UTC day is after `buy_date`. Earlier event not registered and now registered: `newly_registered`. Both registered with known, different creation dates: `re_registered`. Everything else (same state, a drop) writes nothing, so a state is never recorded twice. `ending_id` points at the `engine_endings` row that holds the answer; `created_at` is the job's clock.
- **`engine_endings.registrar`** (nullable) is filled by `saveAnswer` from the RDAP registrar entity's name (`registrarOf` in `core/rdap.ts`); older rows stay null (the same name is in `evidence.registrar`).
- **`ENDING_REGISTERED`** (`reporting/report/warnings.ts`): one warn per non-baseline event created in the last 30 days (`ENDING_REGISTERED_DAYS`). **`GET /owned/:domain/endings`** (`ownedEndingsView`): five current endings and the events; 404 `DOMAIN_NOT_FOUND` for a name that is not owned.
- Not built: a leads-list write (no such list exists; the warning and the route are the list), the hyphen `.com`.

## Hold-time slices (5.7.0, CR-058, `slices.ts`)
`holdSlices` runs at the end of each training over the frozen test rows and is stored in `metrics.slices`; `GET /engine/health` and `GET /engine/train/:id` show it (null for older models; there is no on-demand computation). A sold row is `quick` when its `sale_date` is before the `.com`'s registry creation date + 91 days (`QUICK_SALE_DAYS`), else `held`; no `.com` date (or none answered) = `unknown_n`. Per slice: `n`, `recall` (score >= 0.5, `RECALL_THRESHOLD`: the engine has no other cut-off), `net_pit_share` (rows with `net_pit` = 1 over `n`), `auc` (the slice's sold rows against all unsold test rows; null under 2 rows). Reporting only, not a feature: the `.com` date comes from `computeFeatures().comCreatedMs`, which is the same value the leak guard already handles.

## Free data feed from the daily data save (5.41.0, `ops/jobs/datasave/datasave.ts` `engineFeed`)
The engine had 0 sold and 0 unsold rows; two free, official sources now feed it every day (datasave step `engineFeed`, after `buildPanel`; rules and tests in `datasave.md` "Engine feed"). Both go through `storeUnsold` / `storeSales` (`uploads.ts`), so the duplicate rules, chunked multi-row inserts, one `engine_uploads` row per kind per run (`by` = `datasave`) and the token-index cache key (`max(engine_uploads.id)`) work as for a bot upload.
- **Unsold:** GoDaddy closeout names that left the list before their end and whose RDAP tag is `deleted` (`disappearances`): type `dropped_after_held`, `observation_date` = the day it left the list (`gone_date`), `caught_by_catcher` true for `RE_REGISTERED`, false for `NOT_REGISTERED`, null for a status (redemption / pending delete). A caught row is excluded from training by `dataset.ts` as before. The RDAP daily cap is spent on in-regime names first (`engine/regime.ts` `loadRegimeTest`: the same `inRegime` test and extended split table as training).
- **Sold:** GoDaddy auctions that ended with at least 1 bid and a final price of at least `settings.datasave_auction_min_cents` ($100): `engine_sales`, `price_cents` = final price, `sale_date` = the end day (Israel), venue `godaddy`, source `godaddy_auctions_file`. **Bias:** mostly investor-to-investor wholesale sales, not end-user sales, and the unsold side is cheap closeout names. Training does not separate them yet; `source = 'godaddy_auctions_file'` marks the rows so a later model can drop, weight or slice them (and the 20-day rule applies to them as to every sale).
- **NameBio:** nothing in `features.ts`, `data.ts`, `dataset.ts` or `train.ts` reads a NameBio table (`namebio_keyword_stats`, retail stats); NameBio-derived values reach the engine only if a bot uploads them as `engine_sales` rows (`venue` / `source` text), which the 5.41.0 check found no code path to guard (see the 5.41.0 release note).

## Batching (v5.42.0, G-124)
`EndingsWriter` (`endings.ts`) buffers the bulk pairs' answers and writes every 500 with the same rule as `saveAnswer`: one `update ... from unnest` for unanswered rows, one guarded (`is not distinct from`) update for same answers, one multi-row insert for changed or never-asked pairs; an unanswered re-ask of an answered pair writes nothing. Owned pairs are still written one at a time, because their event reads the row just written. Test BK542-8 (`tests/modules/bulk/bulk-endings.test.ts`) compares the rows with `saveAnswer` and counts queries (700 before, 3 after for 600 answers).
