# Knowledge base (CR-078, G-132; phase 1 built in 5.43.0)

The company's evidence base: sources graded on two axes, claims, the evidence that links them, independence clusters, and a verdict per decision question computed in plain code. Design inputs: `docs/research/knowledge-sources-2026-10.md` §2.2-2.5. Contract: `docs/contract/endpoints.md` §Knowledge base, `jobs.md` step `kbLoad`. Module: `src/modules/knowledge/` (imports nothing from another module; `ops` and `app.ts` import its `index.ts`).

## Rules (binding)
1. **No AI in the server** (founder rule 9). The server stores, deduplicates and computes. Sessions and bots read, extract and grade. `KB543-23` greps the module for model clients.
2. **Free sources, legal access only** (CR-078 rule 2). Phase 1 has no collector; phase 2 (`kbLeads`) is not built.
3. **Two axes.** Source reliability `A|B|C|D|F` (F = not yet judged, weight 0; D is kept for the record, weight 0) with a required reason unless F; item credibility `1..5` judged on the item alone. A source is graded per claim type through `kb_evidence.claim_grade`, which can only **lower** the source's grade for that claim (a marketplace is A for its own sales count, D for "now is a great time").
4. **Independence.** `echo_of`, `syndicated`, `same_author` (needs a note naming the shared data) and `aggregator_of` links put sources into one cluster (union-find over the non-retracted newest link rows); `cites` does not. Per cluster only the strongest item counts, separately for each stance.
5. **Weights are data.** `kb_settings` (versioned, append-only; v1 = research §2.3) holds the topic list, per-topic half-lives, G/C/N/K tables, the N formula constants and every threshold. Changed by migration only (no route, no admin command yet). Nothing in `verdict.ts` is a default.
6. **Verdicts are appended, never edited** (`kb_verdicts`): certainty, plain-word downgrades, clusters used, a snapshot of the inputs (up to 500 items). A new row only when the result hash (settings version, verdict, certainty, downgrades, clusters; numbers rounded to 2 decimals) differs from the latest one.
7. **Append-only tables with versions.** `kb_authors`, `kb_sources`, `kb_claims`, `kb_evidence`, `kb_source_links` carry `version` and `supersedes`; the natural key plus `version` is unique, and `(version = 1) = (supersedes IS NULL)`. A correction is the same key with `"supersede": true`. Evidence and links reference the **first version** of a source or claim; reads take the newest. `kb_questions`, `kb_verdicts` and `kb_settings` are append-only without versions. `kb_loads` is the load log (insert only by convention; one successful row per sha256).
7b. **One writer (6.0.0, CR-098 ask 4; KB-098-3):** a bots or data token may only dry-run `POST /kb/*` (403 `KB_DRY_RUN_ONLY`, `DRY_RUN_ONLY_SCOPES` in `api/kb.ts`). Rows land through a numbered `data/knowledge/` file (`kbLoad`) or a WRITE token. Why: on 26 Oct the `bots-shared` token committed rows that the 0008 file then clashed with (CR-098).
8. **All-or-nothing writes** (`store.ts` `applyKind`): any rejected row rejects the batch (`KB_ROWS_REJECTED`) and nothing is stored. Idempotent by content: identical rows are duplicates; other content under the same key needs `supersede`. One transaction under the `kb_write` advisory lock (routes, loader and verdict append share it).
9. **DOM never posts to production.** DOM's research ships as `data/knowledge/*.jsonl` and is loaded by the daily step `kbLoad`. `data/knowledge/` holds only real knowledge files: `0001-questions.jsonl` (25 decision questions) and `0002-october-research.jsonl` (the October 2026 research: 8 authors, 203 graded sources, 93 claims, 271 evidence rows, 22 links), from 25 Oct 2026. A new research round adds a new numbered file; a correction is a new file with `supersede: true` rows. Files are loaded in name order. The fixture lives in `tests/fixtures/knowledge/`.

## Data model (migration `1766800000000_v5-43-0.sql`)
Tables as in research §2.2 with these deliberate differences:
- **Topics** are not a CHECK: the list is `kb_settings.values.topics` (v1: `sell_through, price_bands, auction_tactics, buyer_types, name_shape, extensions, renewal_economics, safety_trademark, safety_history, marketplaces, platform_rules, other`), so a new topic is a new settings version. The routes reject an unknown topic (`TOPIC_UNKNOWN`); the table only checks the shape `^[a-z_]{2,40}$`. Enums for reliability, credibility, stance, evidence kind, link kind, type, status, direction are CHECKs.
- **`kb_evidence` has its own `effect_value`** (the number that source reports): claims are shared by many sources, so a numeric pool needs one value per source. The claim's `effect_*` stays as its reference value. Also `population_match` (`direct|indirect`, the indirectness input), `survivorship` (the bias input) and `claim_grade`.
- **`kb_claims.option`**: which option of the linked questions the claim supports (when its evidence supports it). Per-option sums need it. `question_ids` is filled from the row's question slugs.
- **`kb_sources.topics`** (for `GET /kb/sources?topic=`), `excerpt` (300 characters), `content_hash` and `minhash` (512 hex characters = 64 x 32-bit hashes).
- **`kb_questions`** are not versioned (a changed question is a new slug).

## Weight and verdict (`verdict.ts`)
- `w = G x C x N x R x K`. `G` grade table; `C` credibility table; `N` for measured items (and reported sales with n > 1) `min(1, log10(n+1) / log_divisor)`, one reported sale 0.1, everything else the fixed 0.3; `R = 0.5^(age_days / half_life_days)` with the age from the claim's `date_range_end` (else the source's publication or retrieval date) and the half-life from the claim or its topic; `K` kind table. A rejected source weighs 0.
- Per option: `W_for` / `W_against` = sum over clusters of the strongest supporting / contradicting item; `agreement = W_for / (W_for + W_against)`. The leading option has the greatest positive net weight and beats the runner-up; a tie has none. A question without options is one open group.
- Numbers: weighted median (and min / max) of the strongest valued supporting item of each cluster.
- Certainty: start moderate if an A cluster with measured data supports, else low. Steps down for inconsistency (agreement below `inconsistency_agreement`), indirectness (indirect share of weight above `indirect_share`), imprecision (fewer than `min_clusters` clusters or total N below `imprecision_total_n`), bias (survivorship or a conflict of interest above `bias_share`), staleness (weight-without-age-weighted mean R below `stale_mean_r`). One step up when agreement is at least `step_up_agreement` and there are `step_up_min_a_clusters` A clusters or an `own_analysis` source supports (deviation: research says "our backtest agrees"; the agreement threshold is applied to it too). `high` needs `min_clusters` clusters, `high_min_a_clusters` A clusters, agreement at least `high_agreement` and no step down. Anything above `very_low` needs `min_clusters` clusters with `min_ab_clusters` A or B (the rep of a cluster is its strongest item). The clusters counted are those bearing on the leading option.

## Echo flags
Same canonical URL = same source (the unique `url_hash`). `GET /kb/echo-candidates`: MinHash over word 5-gram shingles of the excerpt (`minhash.ts`: FNV 32-bit, 64 universal hashes mod 2^32-5 from a fixed LCG; banding 32 x 2 finds candidates), estimated Jaccard at or above `echo_jaccard`, no existing link. A session confirms with `POST /kb/links`.

## Repo load (`load.ts`, step `kbLoad`)
Files `data/knowledge/*.jsonl`, one JSON object per line, `"kind"` = `author|source|question|claim|evidence|link` plus the fields of the matching route row; a link line names the link kind `link_kind` (its `kind` is the row kind); blank lines and lines starting with `//` are skipped. A file is loaded once per sha256 (a successful `kb_loads` row); rows go in kind order in one transaction through the same `applyKind` as the routes (chunks of 1,000), so validation is identical; a bad line or a rejected row fails that file only (a `kb_loads` row with `ok = false` and the error, recorded once per distinct error) and the step summary lists it under `failed` (so the daily step is not ok until it is fixed in a new file). Rows are stored with `by = repo-load`. **v5.79.0 (CR-098):** the load passes `fileBy = repo-load` to `applyKind`: a versioned row whose stored newest version has another `by` (a route call) is appended as the next version without `supersede` and listed in `counts.<kind>.auto_superseded`; a clash with an earlier file still needs `supersede: true`; a question (not versioned) still fails. A reject carries `key` and `fields`, and the loader adds the file `line`, so the error reads `source: N rejected: line L EXISTS_DIFFERENT <key> [fields]`. `runOnce({dryRun: true})` (route `GET /kb/load-preview`) runs all files not yet loaded in one transaction with a savepoint per file and rolls it back. Why: on 26 Oct a bot posted 10 sources by route; 0008 re-researched the same URLs and failed three nights (CR-098). The example file is `tests/fixtures/knowledge/0000-example.jsonl`.
