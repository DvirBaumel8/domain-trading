# Auction bid plans (CR-077, v5.39.0)

Auctions are the main S8 buying line (founder rule 5; at most `settings.s8_max_price_cents` = $250 a name, each with Dvir's approval). This file holds the binding rules and test ids. Code: `src/modules/selection/prebid.ts` (the automatic checks), `src/modules/ops/auctions/plans.ts` (plan logic), `src/modules/ops/api/auctions.ts` (routes), `src/modules/ops/api/portfolio-import.ts` + `ops/admin/import-domain.ts` (the import rule). Tests: `tests/modules/ops/auction-plans.test.ts` (AB539-*), `tests/modules/ops/safety-checks.test.ts` and `tests/modules/selection/unit/brand-typo.test.ts` (SF544-*, v5.44.0), helper `tests/helpers/bid-plans.ts`.

## Flow
prebid (`POST /auctions/prebid`) -> plan (`POST /auctions/plans`, Dvir's line names the maximum) -> bid by hand at the venue -> result (`POST /auctions/plans/{id}/result`) and, for a won name, `POST /portfolio/import`.

## Rules
1. **Prebid checks only registered names**: no availability, price or quote check. Every check is PASS, FLAG, FAIL or SKIP. A check that could not be read is a FLAG (never a pass); only a source switched off by its setting (`sources.surbl`, `sources.popularity`, no Web Risk or Companies House key) is SKIP. Verdict: any FAIL -> `fail`, else any FLAG -> `flag`, else `pass`. The first failing name rule (SPELL-1, BRAND-1, BIGCO-1, TM_KILL) is the FAIL; the later ones are SKIP.
2. **Manual items** (EXACT_STRING_BUSINESS, HIST_WAYBACK) are never automated; the plan must confirm both (`checked: true` + a note). The USPTO trademark search is also manual in the whole service; the prebid covers only the loaded kill terms (TM_KILL).
3. **Prebid is a normal mutating POST** (stores a row): WRITE or bots, Idempotency-Key, audited. `prebid_checks` is append-only.
4. **A plan needs**: an approval validated by `core/approval` (names the domain, <= `settings.approval_max_age_hours`, not future) whose text also names the maximum bid as a dollar amount (`amountsNamed`); a prebid of this name and venue made within the same window with verdict not `fail`; `max_bid` <= the S8 cap (400 `S8_PRICE_CAP`); above $50 `reasons.comparables` or `reasons.other_endings`; kind `closeout` only while `settings.s8_closeouts_allowed` (default false, migration only); an `auction` needs a future `auction_end_at`. One open plan per name (partial unique index + advisory lock `bid_plan:<domain>`). DOM never generates the approval text.
5. **Statuses**: open, won, lost, withdrawn, expired. `expired` is computed in reads for an open plan whose auction ended more than 7 days ago; a new plan for the name stores it (event) so the open-plan rule does not block. Every change is a `bid_plan_events` row (append-only): created, won, lost, withdrawn, expired, imported.
6. **Result**: from open (or computed-expired) only; `won` needs a price and refuses one above the maximum (409 `PRICE_ABOVE_PLAN`, nothing recorded); `lost` may carry the winning price; `withdrawn` takes none. It books nothing.
7. **Import (lane S8, API only)**: needs a plan stored `open` (not computed-expired) or `won`; checked after the S8 price cap and slot checks; price <= `max_bid` (409 `PRICE_ABOVE_PLAN`); no plan 409 `BID_PLAN_REQUIRED`. `approval_ref` may be left out when a plan exists: the plan's approval is used (founder rule 1: Dvir approved this name and price when the bid was committed; an auction may end after the 72 h window); a given `approval_ref` is validated as before, first. In the import transaction an open plan becomes `won` with `final_price = price_paid`; a won plan gets an `imported` event. The ledger note says `bid plan <id>`; the audit row summary names the plan and whether the approval came from it. A dry run reports `would_be_blocked`. The admin `import-domain` command does not enforce plans.
8. Plans and results are WRITE only (`write_only` in `BOTS_ROUTES`); prebid is `allowed` for bots.

## Safety checks added in v5.44.0 (research `docs/research/funnel-names-safety-2026-10.md` §5; free only, Dvir 25 Oct 2026)
9. **Check list and order** of a pre-bid answer: SPELL-1, BRAND-1, BIGCO-1, TM_KILL, TYPO-1, BRAND-TYPO-2, SURBL-1, URIBL-1, SPAMHAUS-DBL, WEB-RISK-1, EUIPO-1, RDAP_STATUS, SAME_NAME_ENDINGS, UK_COMPANY. Every check has `checked_at` (Asia/Jerusalem ISO, set when the check was added); the stored `prebid_checks.answer` keeps it (WIPO Overview 3.0 §3.2.3: recorded screening protects us; §3.9: an expired name is a new registration on the day of the bid, so the check runs at bid time).
10. **BRAND-TYPO-2** (`selection/brand-typo.ts`, wired in `selection/prebid.ts`). Brand labels = the registrable labels of the stored popularity list (the Majestic top `typo.top_n` = 10,000 rows of `reference_files` `popularity_list`, refreshed by the daily `referenceRefresh` step). **Tranco is not used**: it has no licence of its own and one upstream source is CC BY-NC (gap G-30, `popularity.ts`); Majestic's CC BY 3.0 terms were verified. Rules: labels of 4+ letters or digits, hyphens removed; edit distance (Damerau) <= 1 for a brand of <= 10 letters, <= 2 for a longer brand; the same after folding look-alikes (`rn`->`m`, `vv`->`w`, `0`->`o`, `1`->`l`, `i`->`l`) on both sides; a brand of >= 5 letters contained in a longer name is a combosquat; an identical label is `exact`. Severity FAIL, except **FLAG** when the contained brand (combosquat) or the name's own label (typo, look-alike) is an ordinary word of the frozen list `data/wordlists/en-scowl-35-lower.txt` (lowercase SCOWL 35: `apple`, `target`, `time`, `stack` are words; `paypal`, `google`, `amazon` are not). Exact is always FAIL. No list, a list older than `typo.max_list_age_days`: FLAG; `sources.popularity` off: SKIP. TYPO-1 (distance 1, top 10,000) still runs and fails first. The check is not added to screening (not trivial: screening plans and packs are versioned selection settings).
11. **URIBL-1** (`selection/checks/surbl.ts`, `uriblCheck`): `<name>.multi.uribl.com` A lookup through the same machinery as SURBL (`dnsblCheck`: zone name servers asked directly, a control name that must be listed proves a server, a refusal answer 127.0.0.1 or REFUSED is `QUERY_REFUSED`, SERVFAIL `SOURCE_ERROR`, no answer `TIMEOUT`, no provable server `CONTROL_FAILED`; all of them FLAG, never PASS). Bits: 2 black, 4 grey, 8 red. **Black -> FAIL, grey or red alone -> FLAG.** Switch: `sources.surbl` (one switch for both DNS lists); zone, control name `test.uribl.com` and bits are constants in the file (`URIBL_ZONE`), not selection settings. Not verified live on 25 Oct 2026: the zone's authoritative servers and the control name must be confirmed on the first live run (until then an unprovable zone shows as a FLAG `CONTROL_FAILED`, which is the safe way to fail). Terms (read 25 Oct 2026, https://uribl.com/datafeed_faq.shtml): the paid datafeed is needed only "if you provide commercial services which query URIBL" or above 100k queries a day; we sell no service built on it and ask a few names a day for our own buying, so the free public lookups fit.
12. **SPAMHAUS-DBL**: always SKIP, reason `not used: free Spamhaus access is non-commercial only` (the free DQS key is non-commercial; we are commercial). No live call is built. It stays in the answer so the gap is visible.
13. **EUIPO-1**: always SKIP: `not automated: the EUIPO Trademark Search API needs an API key the founder must create himself (none is configured); search EU marks by hand (TMview)`. The existing EU check (`tm_eu`, `eu_tm.required_lanes` = S6 only) stays manual in screening. When the founder creates a key, the live call is a follow-up (the check id is reserved); never a PASS without it.
14. **Manual search strings**: `manual_required[EXACT_STRING_BUSINESS]` carries `name_as_words`, `camel_case` and `search_strings` (`"bright widgets"`, `"BrightWidgets"`, `"brightwidgets"`, `site:opencorporates.com ...`, `site:find-and-update.company-information.service.gov.uk ...`, `site:companieshouse.gov.uk ...`); `HIST_WAYBACK` carries `wayback_url`. Words come from the form rule's tokens (the name itself when it has none). Nothing is sent to Google.
15. **After-auction transfer check** (`POST /portfolio/import`, lane S8; `ops/admin/import-domain.ts`, `ops/jobs/portfolio-check.ts`, `reporting/report/warnings.ts`). The import reads RDAP (`core/rdap` `rdapLookup`, read-only) and compares RDAP's registrar with the import's `registrar` by `registrarMatches` (`core/rdap.ts`, shared with the registry check: godaddy, porkbun, dynadot by name, else a case-insensitive substring): `transfer_confirmed` true / false (another registrar, or not registered) / null (unreadable, or no RDAP given: the admin command). Stored in `domains.transfer_confirmed` and `transfer_checked_at` (migration `1766900000000_v5-44-0.sql`), returned in the import answer. Anything but true: warning text in `warnings` and the `/report` warning `S8_TRANSFER_UNCONFIRMED` (warn, `reporting/report/warnings.ts`). The daily `portfolioCheck` step (its registry check) rewrites the two columns of an S8 name while it is not true, then stops. Listing is not blocked by the server; the warning says not to list until the transfer is complete. S8 names imported before 5.44.0 start with null and get their first answer from the next daily step.
16. **Not built (item 7, bid-plan age):** "a plan whose prebid is old" is already covered: a plan needs a prebid made within the approval window (72 h, rule 4), so the trademark and blocklist checks are never older than 3 days when the bid is committed. A stricter 7-days-before-`auction_end_at` rule was skipped (not simple, no new evidence behind it); `checked_at` per check is the evidence.

## Shortlist (v5.45.0, G-127; Dvir 25 Oct 2026, top-down review finding 2)
The daily datasave step `auctionShortlist` (after `engineFeed`) hands Gavriel a short, pre-checked list of the best live GoDaddy auctions in our range; Dvir decides. Code: `ops/auctions/shortlist.ts` (`runAuctionShortlist`, `getShortlist`, `getFunnel`), `ops/auctions/shortlist-score.ts` (pure score and the maximum-bid rule), `ops/auctions/prebid-store.ts` (`storePrebid`, shared with `POST /auctions/prebid`), `engine/endings.ts` (`askEndingsFor`, `endingsState`, `endingDue`), `ops/api/auctions.ts` (the two GET routes). Table `auction_shortlist` (migration `1767000000000_v5-45-0.sql`, not in the backup: derived daily data) and `settings.shortlist_*`. Tests: `tests/modules/ops/auction-shortlist.test.ts`, `tests/modules/ops/unit/shortlist-score.test.ts` (AS545-*).
17. **Candidates:** `godaddy_auctions_live` of the newest data date; `end_time` in the next `shortlist_horizon_hours` (72); price <= the S8 cap; >= 1 bid; `.com` with one label. **Hard filters (offline, no outside call):** names in `domains`, names with an `open` or `won` bid plan, `closeoutNameChecker` (SPELL-1, BRAND-1, BIGCO-1, TM_KILL, the same loaded lists as the pre-bid), names whose maximum bid is not above the price, and BRAND-TYPO-2 (rule 10) against the stored popularity list. **v5.72.0 (CR-088):** all names that pass the hard filters are stored, not just the top `shortlist_size`; the brand check runs on every ranked candidate (no pool size cap). If more than 10,000 names pass, the step stores none and sets `status: 'field_exceeds_10k'` with a warning (talk to Dvir). `settings.shortlist_size = 0` means store all (the new default; a nonzero value still caps). No list, an old list or `sources.popularity` off: the filter is skipped and the summary says `no_list`, `old_list` or `off`. An ordinary-word brand match (a FLAG) keeps the name with a reason.
18. **Maximum bid (v5.48.0, F22: Dvir chose option (b), expected value, 26 Oct 2026):** the chance that a shortlisted name sells within our hold (`settings.shortlist_sale_chance_bp`, default 10%) times the expected net resale (`settings.shortlist_expected_resale_cents`, default $1,000, a realistic end-user price from the knowledge base question `end-user-price-band`, not our list price, less the commission of the selection setting `buy.commission[buy.math_venue]`, Afternic 20%), less the one renewal we pay while holding (`settings.shortlist_renewal_cents`, default $23 since v5.49.0, P5: GoDaddy renews at about $23, `report.json` $23.19 and $23.00; was $11): $80 - $23 = $57, so **$55 at full score** (was $65). Scaled by the final auction score (full from `SCORE_FULL_MAX` = 85, proportionally less below), never above `settings.s8_max_price_cents`, never below 0, rounded down to a whole $5. A name whose scaled maximum is not above its current price is dropped (no headroom). The 10% is about 3x the published chance for a 2-year hold (sell-through about 1.7% a year, round-3 research): it assumes our picks sell better, and only our own outcomes (won names' views, leads, sales) may raise it, by migration. History: v5.45.0-v5.47.0 used 20% of the net resale ($160 at full score), which loses money on average under the 2-year hold (round 3, F22); the first v5.45.0 draft used the S8 ladder BIN, which put every name at the $250 cap.
18a. **Position (v5.48.0):** each stored row keeps `field_n`, the auctions that passed the filters that day; the route shows `top_pct` = rank / field_n. Scores bunch while the lift table has only seed data, so the position is the honest reading of the rank.
19. **Auction score v1** (0-100, `AUCTION_SCORE_VERSION = 'auction-v1'`, stored with every row; hand weights from research round 2 `round2-score-and-data-2026-10.md` section 2, joint cell section 3.3): **name part 60** = shape and the other endings. Shape = one joint cell of words (1-2 / 3 / 4+) by letters before .com (<= 8 / 9-12 / 13-15 / 16+), values 1.0 / .85 / .55 / .25 for 1-2 words, half of that for 3 words, a fifth for 4+; the other endings (net, co, org, io, ai) as asked: 0 registered 0, one 0.5, two or more 1. Inside the part shape weighs 25 and the endings 30 (round-2 S and R weights), and the endings weigh `30 x known/5`: **an ending nobody could check is unknown, its weight leaves the part (rescaled), never a 0**. **Price headroom 20** = `1 - price / max bid`. **Bids 10** = `ln(1 + bids) / ln(21)` capped at 1 (20 bids = full), **halved when the SEO look applies: `domain_age` >= 10 years and `pageviews` > 0 in the file** (the file gives no traffic figure besides `pageviews`). **Age 10** = `min(1, years / 10)`; an unknown age leaves the part out (rescaled). Total = known points / known maximum x 100, one decimal. **GoDaddy's `valuation` is stored and shown, never scored** (research: appraisals are unreliable). Not in v1 (no free offline source): live-business count on other endings, buyer-pool list, keyword demand, the "registered before the .com" bonus.
20. **Other endings fetch:** after the pre-rank (score without endings), the pool names whose five endings are not all answered within 30 days (never asked, unanswered for 6 hours, or older than `ENDINGS_STALE_DAYS`) are asked in rank order, at most `shortlist_endings_n` (50) names, 2-minute budget, through the engine's own code (`askEndingsFor`: RDAP only, per-host pacer, 4 in flight per host, `EndingsWriter` keep/update/append rule). Skipped while the daily `engineEndings` job holds its lock. The budget running out or one registry refusing leaves those pairs unknown. Final score and rank use whatever `engine_endings` holds (even an old answer counts as known).
21. **Stored list (v5.72.0, CR-088):** all hard-filter passers (when `shortlist_size = 0`, the default since 5.72.0; a nonzero value caps to that many) by final score (ties: earlier end, then name), written in one transaction that first deletes the data date's rows. `rank` is the position before pre-bid drops. `reasons` are plain-language lines. Typically 500-750 names/day.
22. **Automatic pre-bid:** walking down the list, `storePrebid` runs `runPrebidChecks` (venue `godaddy`, token name `datasave`, audit null) until `shortlist_prebid_n` (10) names did **not** fail, trying at most 3 x that many names inside an 8-minute budget; a stored pre-bid of the same name younger than 12 hours is reused. A `fail` sets `dropped_reason` (`<check id>: <reason>`) and the route leaves the name out. One name erroring (`errors_n`) never fails the step. The prebid id is valid for a plan for 72 hours (rule 4).
23. **`GET /auctions/shortlist`** serves the non-dropped rows of a data date whose auction has not ended, by rank, with the pre-bid (`id`, `verdict`, `checked_at`, `valid_until`, `flags`). **v5.72.0 (CR-088):** pagination with `limit` (1..10,000, default 25) + `offset` (>= 0, default 0); `total` is the count of all eligible rows for the date, so a client can page the full field. **Three counts (do not confuse):** (1) **`field_n`** on each row = hard-filter passers **stored** when `auctionShortlist` ran that day (the full field size; used for `top_pct`). (2) GET **`total`** = rows still **live-eligible to serve** now (not ended, not left out for a failed auto-prebid). It is often lower than `field_n` because auctions end between build and read — that gap is not an artificial cut. (3) **Buyer-judged** = how many of the served rows Buyer actually processed in a discovery run (after prior excludes); report it separately. **Do not prune** ended or prebid-failed rows from storage by default: they stay for paper/replay/funnel; GET simply leaves them out of `rows` / `total`. **`GET /auctions/funnel`** counts, per table, one query each: live auctions seen, shortlisted and served, auto pre-bid verdicts, bot pre-bids (token name other than `datasave`), plans by status, imports, S8 names bought / listed / sold, their latest views and leads, sales. Both are read only.
24. **Gavriel's daily routine** (impact): read `GET /auctions/shortlist`, show Dvir 3 to 5 names with the suggested maximum and the reasons, and after Dvir's line create the plan (`POST /auctions/plans`) with the `prebid.id` (a fresh pre-bid can also be made with `POST /auctions/prebid`).

## Auction score v2 (v5.46.0, first live run problem 2)
`AUCTION_SCORE_VERSION = 'auction-v2'` (new rows; stored `auction-v1` rows stay readable). On 25 Oct the top 25 all scored 84-94 (every one got the full $160) and coined strings the splitter reads as two words (thrune, foamira, idward, finsplat, dnasays) scored like real phrases. Changes, all in `ops/auctions/shortlist-score.ts` and `ops/auctions/word-quality.ts`:
1. **Word quality** (0..1 = half the weakest word's level + half the mean). A word's level comes from frozen offline data: curated trade / tech / regime words of the `bt1@v3` split file (class `special`) and SCOWL size 35 lowercase (`commonWord`) = 1; other pieces by their SCOWL level in the split file (the engine's zipf proxy is the same data): level 35 names and abbreviations 0.6, 40 = 0.5, 50 = 0.7, 60 = 0.35 (widget), 70 = 0.2, a place-only piece 0.5, unknown 0.05; a 2-letter piece at most 0.3 (0.75 if on the curated list: ai, hq). **Common = level >= 0.7.** The name part is multiplied by the quality, and **a name with a word that is not common is capped at `50 x (0.5 + 0.5 x quality)`** (never above 50; about 35 for a coined string).
2. **Graded shape:** the length axis is interpolated between the band anchors (6, 11, 14, 18 letters) instead of steps, so 8, 10 and 12 letters differ.
3. **`SCORE_FULL_MAX` 70 -> 85:** the maximum bid is full only from 85 (linear below). On the sample below a good real phrase (score 76-84) gets 90-97% of $160, a coined string (35-43) 41-50%.
4. The words come from the form tokens (`closeoutNameChecker`), not a separate split.
Sample (price $50 of a $160 maximum, 5 bids, 5 years old, endings unknown): vetday 84.7, gymnest 82.9, finsplat 81.1, cozyfleece 77.5, kingscapes 77.5, makeplastic 75.7, reachhq 72.0, brooklynair 64.2, dnasays 42.5, foamira 40.6, comphost 37.8, gatherms 36.9, idward 36.9, thrune 35.0, laptopi 33.8. **Known limit:** finsplat (fin + splat) is two ordinary dictionary words, so no offline list separates it from a real phrase; the trained engine (later) has to. The score drops by about 10-15 points when the other endings are all free instead of unknown.

## Auction score v3 (v5.47.0, F5, F8, F20)
`auction-v3` is stored when a lift table exists (`lift_models` has a row); without one the v2 score is used unchanged. (1) **Name part from the lift:** name part = word quality x (lift score / 100), replacing the hand shape + endings part; word quality stays the gate and the uncommon-word cap stays. The lift gets length and word count from the engine split, and the other endings asked (registered count and share) when the shortlist asked them; without endings those patterns are skipped (`engine.md` "Lift model"). `parts.name.lift {sum, score, bins}` and a `lift ...` reason line show it. (2) **Bids worth 5 points** (was 10; F8, investors-deep research: high bid counts are investors competing, not end users, and bidder pairs inflate them). Applies to v3 only. ## Auction score v4 (v5.49.0, improvement pass 26 Oct, P2 and P3)
`auction-v4` is stored when a lift table exists (v3 before; without a table v2 is unchanged). On 25-26 Oct 22 of 24 names got the same $65 and the top names sat at 95-99 "sold-like". Changes, in `ops/auctions/shortlist-score.ts`, `shortlist.ts`, `word-quality.ts` and `engine/lift.ts`:
1. **`registered_share` served as unknown.** The lift's share feature was trained on 20 sibling names (CR-002), not on the share of the five own endings, and both features came from the same five lookups (one registered ending gave the capped +2 twice). `endings_before` is kept.
2. **Empty lift bins count 0** (`scoreLift(..., {emptyBinZero: true})`, used by the shortlist only): a bin with no row at all on either side (a shape outside the seed's range: 1 word, 4+ words) adds 0 instead of the pattern's lowest lift; a thin bin that has some rows keeps the old rule (the engine's own scoring is unchanged).
3. **Headroom is a filter, not points.** A $1 price says "uncontested so far", not "cheap" (68% of 1-bid $1 names stayed at $1, 13% reached $65+). The filter "the maximum bid is above the price" stays (`dropped.no_headroom_n`).
4. **Weights (v5.51.0):** name 30, demand 40, age 25, bids 5 (sum 100; an unknown part is rescaled out). v5.49.0 shipped 70/15/10/5; the backtest on our own 148 sold / 553 unsold names (`docs/research/backtest-production-2026-10-26.md`) found other endings with a live site (AUC 0.78; 0.80 on names aged 5+) and age the strongest signals, and the name part near a coin toss. No v4 shortlist had been stored yet, so the version stays `auction-v4`. The uncommon-word cap is skipped when `developed_tlds` >= 1. `parts` has `name`, `bids`, `age`, `demand` (no `headroom`).
5. **Demand (P3, free, every name, no lookups)** from the GoDaddy file fields stored in `godaddy_auctions_live` (`exact_match_tlds`, `developed_tlds`, `keyword_registrations`, `search_volume`, `cpc_cents`; null = not in the row; parser `ops/jobs/datasave/auction-fields.ts`): `0.6 x developed endings` (0 -> 0, 1 -> 0.5, 2+ -> 1; other endings with a live site, our strongest signal) `+ 0.4 x exact-match endings` (ln(1+n)/ln(11), 10+ full). One missing: the other alone; both missing: the part leaves the score (rescaled like age), `known: false`. In the 706 in-range auctions of 26 Oct the share reaching $100+ rose from 9% (1-2 exact-match endings) to 59% (6-14). `keyword_registrations`, `search_volume`, `cpc_cents` are stored but not scored yet (no evidence for a weight).
6. **Name part = the name's position in the day's field.** The raw value is word quality x lift/100; every candidate of the day (`cands`, after the hard filters) is placed in the sorted field and the part is `70 x percentile` (share of the field below plus half the ties). The final score of a pool name (endings now known) places its new raw value among the field's raw values. Reason line: `lift +x (...): name in the top N% of today's field (field_n names)`. `parts.name.raw` and `parts.name.field_pct` show both.
7. **Short split pieces:** a piece of 3 letters or fewer that is not on `SHORT_WORDS` (about 55 short words that real brand names use: app, pro, hub, lab, vet, day, gym, ...) counts at most 0.5 (`insare` = ins + are scores below `vetday` and `gymnest`). Two-letter pieces keep their 0.3 / 0.75 rule.
8. The suggested maximum keeps `maxBidRule` scaled by the final score (`SCORE_FULL_MAX` 85); it now differs by name because the score does.

## Paper trading (v5.49.0, P4)
Nothing measured whether the shortlist or the $55 maximum would win anything. Code `ops/auctions/outcomes.ts`, table `auction_outcomes` (migration `1767400000000_v5-49-0.sql`, derived data, not in the backup). **Nothing bids or buys.**
- `recordOutcomes` (end of the shortlist step): one row per (data date, name): group `shortlist` = the served top names (rank, score, suggested maximum, first price, end time) and group `control` = 25 names of the same field (`cands`) that are NOT in the list, the smallest `md5(domain || data_date)` (deterministic, random in effect). A second run of the day replaces the date's set.
- `updateOutcomes` (start of the shortlist step, after the inventory step stored the newest snapshot; three bulk statements): open rows take the newest `godaddy_auctions_live` row of the name (last price, bids, snapshot date; an extended end time moves the row's end). A row is **final** when its end time has passed and a snapshot of a later UTC day than the end day exists. The final price is the ended-auction tracker's (`godaddy_auctions`, followed from $100) when it has the name, else the last price seen. `would_win` = suggested maximum above the final price (shortlist rows only; control rows record the final price and keep `would_win` null). Rows older than 120 days are deleted.
- **Reading it honestly:** an untracked auction (never reached $100) can rise after the last snapshot, up to just under $100, so the last price seen is a lower bound and `would_win` an upper bound, until a final-state source exists (the next day's file, or an RDAP check). The control answers "what does a random in-range auction cost to the end" (`reached_100_n`); the shortlist is better than random only if its final prices and its share that stay under the maximum differ from it.
- `GET /auctions/funnel` adds `paper: {shortlist: {final_n, would_win_n, median_final_price_cents}, control: {final_n, median_final_price_cents, reached_100_n}}` over the data dates of the range (`null` median when no final row).
- **Machine competition (v5.65.0, F43):** over the *final* rows of the range, each group (`shortlist`, `control`) also carries `bands` (count by final price: `opening` <= $1, `low` $2-24, `mid` $25-99, `high` $100+; final price = last price seen or the tracker's), `median_final_bids`, and `price_jump` = `{median_cents, jumped_50_last_window_n}` (median of final price minus the first price we saw; count of names whose last seen price is >= $50 above the price seen one snapshot earlier, `auction_outcomes.prev_seen_price_cents`, set by `updateOutcomes` only when a later snapshot arrives; null prev = not counted). The shortlist also has `lost_at_max_n` (final and `would_win` false: ended above our suggested maximum) and `lost_at_max_share` (= `lost_at_max_n / final_n`, 3 decimals, null when no final row). One grouped SQL query. Reading: a high `lost_at_max_share` on the shortlist against a lower share of control `high` says machine buyers contest our picks; a large `jumped_50_last_window_n` says the price moves in the last snapshot window (the "bid late at our max" rule is not tested here, the data only shows the jump). Tests PT43-1..5 (`ops/auction-shortlist.test.ts`). Migration `1768500000000_v5-65-0.sql` adds the column.
- The step summary adds `outcomes_update {deleted_n, seen_updated_n, finalized_n}` and `outcomes {shortlist_n, control_n}`; an error in either is reported there and never fails the step.
