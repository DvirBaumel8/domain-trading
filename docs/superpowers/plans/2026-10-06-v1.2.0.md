# v1.2.0 (CR-001 P1b, outreach-only leads per CR-002) Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Ship contract v1.2.0 (additive only): the CAP-19 screening pack with FLAG verdicts, the CAP-09 manual EU trademark record, the CAP-12 same-name check, outreach-only lead verification (CAP-15/16) with erasable personal data, same-run recompute after a manual history record, and a fix for the jobs-trigger workflow.

**Architecture:** Everything plugs into the v1.1.0 screening mechanics. New checks are registry plug-ins (`src/screening/checks/*`), manual records go through the existing `POST /screening/runs/{id}/manual`, and new thresholds are selection settings with zod `.default()`s, so the immutable stored `v1` row still parses. The pack is a pure assessment (`src/screening/pack.ts`) over the run's in-force results, frozen into an append-only table. Lead verification is a small async worker modelled on `ScreeningWorker`, resumed by the hourly tick. Personal data lives only in an erasable `lead_contacts` table, and is hashed in the audit log.

**Tech Stack:** Node 22 ESM, TypeScript strict, Fastify 5, zod v4, Kysely + Postgres 16, node-pg-migrate (plain SQL), Vitest + MSW (network blocked). No new dependencies.

**Spec:** `docs/requests/CR-001-selection-checks.md` (§3, CAP-09, CAP-12, CAP-14/15/16, CAP-19, §11 P-1/P-5/Q13/Q14), `docs/requests/CR-002-v10-checks.md` (CAP-12 changed, CAP-14/15/16 outreach-only, CAP-20 order, Amendments A and B), `docs/contract/*` v1.1.0, `docs/internal/gaps.md` (G-3, G-8, G-62), `.superpowers/sdd/2026-10-06-cr001-p1a/progress.md` (backlog lines 42 and 45).

## Global Constraints

- **Contract v1.2.0 is MINOR, additive only.** No route, field or code removed or renamed; no existing call refused where v1.1.0 accepted it. `/buy` does **not** require a pack (that is v2.0.0, G-3/G-58).
- **Ruling R-A (`would_be_blocked`):** the v1.1.0 contract types it as the literal `"BUY_HOLD"`, meaning "a real buy is refused now". v1.2.0 leaves it unchanged. A dry run adds `screening_pack {status, pack_id, version, issued_at}` and `advisories: ["SCREENING_PACK_REQUIRED"]` when no complete pack exists. A real buy is not refused for this in v1.2.0. (This deviates from the brief's `would_be_blocked: "SCREENING_PACK_REQUIRED"`; the controller can override it before Task 4.)
- **Selection settings rows are immutable** (`selection_settings_guard`). Every new settings key is added with a zod `.default(...)` that holds the full literal value. `DEFAULT_SELECTION_VALUES` gets the same values. The stored `v1` row must still parse and must receive these defaults.
- Every threshold is a selection setting (exact keys and defaults are in Task 1). Do not hard-code these numbers in logic.
- **No new external source before `docs/internal/sources.md` has its entry.** Task 2 adds "Business websites (operator and firm home pages)" **before** `sources.business_sites` is read by any code. Never fetch LinkedIn. Honour robots.txt. Use an honest `USER_AGENT` (`src/rdap.ts`). Pace requests with the existing `Pacer`. Send no email.
- **Fail closed:** a failed lookup is never stored as clean, free, not-registered or 0. An unknown site is never `none`.
- **Personal data** (email, named person, email-source and role-evidence URLs) lives **only** in `lead_contacts`:
  - it never goes in `screening_evidence` text, `audit_log` (hashed by `redact`), a response body stored in `idempotency_keys`, `lead_batches.input`, or the git backup export;
  - erasure leaves a tombstone.
- **No LLM calls.** No email or chat. Read-only toward the outside world.
- Errors use the format `{"error":{"code","message","details"}}`. Body validation errors return 422 `VALIDATION_ERROR`. Every new route and code goes into `docs/contract/endpoints.md` in the same task, so `tests/contract/contract-doc.test.ts` stays green after every task.
- Use the existing patterns: `AppError`, `storeEvidence`, `lookupCached`/`rdapBaseFor`/`Pacer`, `visibleText`/`ogSiteName`/`hiddenSignals`, `businessNameCandidate`, `makeMatcher`, `readCapped`, `canonicalJson`, `requireNamedApproval` (not needed here), `toResultRow`, `beats`/`latestByCheck`, the `screeningHarness` test helper.
- Commit after each task. Push to `main` (no branches). Each commit message ends with the two attribution lines from the session.

## Review Focus

1. **The stored `v1` settings row after the schema change.** A reasonable person expects every v1.1.0 route that reads settings (runs, tranches, `/selection/settings`, drafts based on `v1`) to work exactly as before, with the new keys filled from the defaults. **Task 1** pins this: parse the seeded DB row, draft from `v1` with a new-key path, and run a v1.1.0-shaped run end to end.
2. **A same-name site that answers but can't be read** (robots disallow, timeout, 5xx, TLS error, a redirect loop, a 512 KB+ page). This must never be read as "no operator". **Task 2** pins it with one MSW case each. Each must come out `site_state: "unknown"`, and the check must FLAG `SITE_UNKNOWN`, not PASS.
3. **A pack issued while the evidence moves:**
   - a FLAG verdict given for an older result id;
   - a manual record posted after the verdict;
   - a quote that goes stale between run and pack;
   - the same content posted twice.

   Expected: the verdict doesn't carry over to a new row; the pack is incomplete with `STALE_QUOTE`; posting the same content twice returns 200 `unchanged: true` with no new version. All pinned in **Task 4**.
4. **Personal data leaking into append-only places** (`audit_log.request`, `screening_evidence`, `lead_batches.input`, the idempotency response, the backup export). **Task 6** pins it with one test that searches every one of these for the raw email string after a batch and an erasure.
5. **Reopening a finished run for a recompute** while a poll, tranche admission or a second manual record runs at the same moment. Expected: no duplicate auto rows for the same (item, check) after the stale one, status goes back to `done`, and the stale row is still visible in `results` history. **Task 3** pins it with two manual history records posted back to back and a poll in between.

export const MANUAL_CHECKS = ['web_risk', 'tm_us', 'history', 'tm_eu'] as const;
const EuMark = z.object({ mark: z.string().max(200), number: z.string().max(40), owner: z.string().max(200), status: z.string().max(100), register: z.enum(['euipo', 'wipo', 'ukipo', 'tmview']) }).strict();
export const TmEuManual = z.object({
  checked_by: z.string().trim().min(1).max(80),
  registers: z.array(z.enum(['euipo', 'wipo', 'ukipo', 'tmview'])).min(1).max(4),
  register_urls: z.array(z.string().url().max(500).refine((u) => u.startsWith('https://'), 'an https URL')).min(1).max(10),
  result: z.enum(['clear', 'hits']),
  exact_or_core_live: z.array(EuMark).max(50),
  generic_live: z.array(EuMark).max(50),
}).strict().superRefine((r, ctx) => {
  const n = r.exact_or_core_live.length + r.generic_live.length;
  if (r.result === 'clear' && n > 0) ctx.addIssue({ code: 'custom', path: ['result'], message: 'result "clear" with marks listed' });
  if (r.result === 'hits' && n === 0) ctx.addIssue({ code: 'custom', path: ['result'], message: 'result "hits" needs at least one mark' });
});
export function tmEuFromManual(rec: z.infer<typeof TmEuManual>, evidenceUrl: string, checkedAt: Date, note?: string): CheckOutcome {
  const fields = { ...rec, evidence_url: evidenceUrl, checked_at: checkedAt.toISOString(), note: note ?? null, source: 'manual' };
  const extra = { dataAsOf: checkedAt };
  if (rec.exact_or_core_live.length > 0) return outcome('FAIL', 'TM_LIVE_MARK', `Live EU/international mark on the exact or core phrase: ${rec.exact_or_core_live.map((m) => `${m.mark} (${m.register} ${m.number}, ${m.owner})`).join('; ')}`, fields, extra);
  if (rec.generic_live.length > 0) return outcome('FLAG', 'TM_GENERIC_HITS', `Live EU/international marks only on a generic phrase: ${rec.generic_live.map((m) => `${m.mark} (${m.register} ${m.number})`).join('; ')}`, fields, extra);
  return outcome('PASS', null, null, fields, extra);
}
export const tmEuCheck: Check = {
  id: 'tm_eu', gate: 'G7', ruleIds: ['TM-1-EU'], lists: [],
  async run(ctx) {
    if (!ctx.settings.eu_tm.required_lanes.includes(ctx.item.lane)) return outcome('PASS', 'NOT_REQUIRED_FOR_LANE', `EU trademark search is required only for ${ctx.settings.eu_tm.required_lanes.join(', ')} (eu_tm.required_lanes)`, { required: false });
    return outcome('MANUAL_REQUIRED', 'MANUAL_SOURCE', `EUIPO/WIPO/UK IPO are not automated: search and record it. ${HOW}`, { required: true, registers: ['euipo', 'wipo', 'ukipo'] });
  },

- [ ] **Step 4: Implement `src/screening/site.ts`.** Key rules:
  - **`fetchPage`:**
    - Robots: read `robots.txt` for the host once (pace it too) and cache it in the `robots` map. A 404 or 410 means allow everything. A robots fetch timeout or 5xx means **unknown** (`ROBOTS_DISALLOWED` is not used; return `kind: 'unknown', reasonCode: 'SOURCE_ERROR'`) and the page is not fetched.
    - Redirects: `redirect: 'manual'`, at most `maxRedirects` hops, each hop paced.
    - Body: `readCapped(res, maxBytes, contentType)`. A cut body is `kind: 'unknown', reasonCode: 'TRUNCATED'` (a harmful or business line could be past the cut; fail closed).
    - Errors: map `ENOTFOUND`/`EAI_AGAIN` (NXDOMAIN only) to `no_site`/`DNS_NXDOMAIN`, `ECONNREFUSED` to `no_site`/`CONNECTION_REFUSED`, the abort timeout to `unknown`/`TIMEOUT`, and a cert error to `unknown`/`TLS_ERROR`. 4xx is `no_site`/`HTTP_4XX`; 5xx and 429 are `unknown`/`HTTP_5XX`.
    - Try `https://` first. Only on `CONNECTION_REFUSED` or `TLS_ERROR`, try `http://` once.
  - **`classifySite` order:**
    1. `ok:false` → `no_site` → `registered_no_site`; otherwise `unknown`.
    2. Final host minus `www.` ≠ expected host → `redirect_off_domain`.
    3. A parked or for-sale signature (`makeMatcher` over `visibleText(...).text` + `hiddenSignals(html)`) → `parked_or_for_sale`.
    4. Visible text shorter than `min_visible_chars` → `registered_no_site`.
    5. Otherwise `in_use`. Then `businessNameCandidate({ html, title, text, timestamp: '' }, ourCom)`: `nameIsDomain` true → `business_name` (`business_name` = its name). Otherwise `phraseUse(text, tokens, markers)`.
  - **`phraseUse`:**
    - Find whole-word occurrences of the tokens joined by one space, or by nothing (`promptinjectionaudit`), case-insensitive.
    - An occurrence is product-style when every token is capitalised in the source text, or a product marker follows within 3 characters.
    - Any non-product occurrence → `service_description`. Only product-style occurrences → `product_name`. None → `none`.
    - Linear scan only (no backtracking regex over page text), at most the first 200,000 characters.

export function requiredChecks(lane: Lane, plan: CheckId[], s: SelectionValuesT): CheckId[] {
  const req = plan.filter((c) => !s.pack.exclude_checks.includes(c));
  for (const c of s.pack.require_checks) if (!req.includes(c)) req.push(c);
  if (s.eu_tm.required_lanes.includes(lane) && !req.includes('tm_eu')) req.push('tm_eu');
  if (!s.eu_tm.required_lanes.includes(lane)) return req.filter((c) => c !== 'tm_eu');
  return req;
}

//   !r -> NO_RESULT ("not in this run's plan" when !plan.includes(c): "draft a settings version whose run.gates include it");

//   FAIL | UNKNOWN | MANUAL_REQUIRED | NOT_RUN -> code = status.

In one transaction: insert the batch, then one `lead_contacts` row per lead (with `email_sha256`), then set the batch `input` with `contact_id`s. Then `leadWorker.kick`. The response is `{ batch_id, status, leads_n, poll }`, with **no personal fields**.

`LeadWorker.execute(batchId)`, for each lead with no `lead_results` row, in order:
1. Settings come from `settings_label`.
2. A firm host in `social_hosts` → `not_qualified SOCIAL_ONLY`.
3. A `never_pitch` match (host, `sha256:` of email, or `firm_name` tokens equal to our SLD's form tokens → `NAME_MATCHES_OUR_SLD`) → `excluded NEVER_PITCH` / `NAME_MATCHES_OUR_SLD`.
4. `weakerDomainReason` `none` → `not_qualified STRONG_DOMAIN`.
5. Fetch the email source page, the firm home page, the size and role pages (skip `never_fetch_hosts`; dedupe URLs; one batch-wide `Pacer(lead.verify.min_ms_between_fetches, 1, sleep)`; a robots map). A fetch that isn't ok → `unverified FETCH_FAILED` / `ROBOTS_DISALLOWED` / `TIMEOUT`.
6. The service phrase on the home or source page → else `not_qualified SERVICE_NOT_ON_SITE`.
7. `emailCheck` → `not_qualified <code>`.
8. Size, role and tier.
9. `enterprise_flag` (phrases, or a bigco list token match on `firm_name`) → `status qualified` but excluded from A/B counts (reason `ENTERPRISE_FLAG`).
10. D1 for the D1 prospect types (pack form PASS with no unknown tokens; distinct unrelated hosts from the pack's `same_name` operators plus the term-use URLs classified by `phraseUse`/`businessNameCandidate` ≥ `d1_min_unrelated_users`; pack `tm_us` PASS). Without a pack: `d1_eligible null`, reason `NO_PACK`.
11. `eu_firm` = the host's last label is in `eu_cctlds`.
12. Evidence: `storeEvidence` with `text: ''` (hash and URL only).
13. Insert the result row.

Deadline or stop: the remaining leads get `unverified TIMEOUT` and the batch is `partial`. Otherwise `done`. In both cases store `summary = leadCounts(...)`.

`GET /leads/batches/:id` (READ) → `{ batch_id, domain, lane, status, pack_id, created_at, finished_at, leads: [result fields + contact { email, email_source_url, named_person, role_evidence_url, erased: bool }], counts }`.
