# Release v5.78.0 (29 Oct 2026)

**Contract:** 5.78.0. No route, field or error change. Two migrations (`1769100000000_v5-78-0.sql`, `1769100000001_v5-78-0-market-names.sql`).

- **What changed (CR-095 part 2):** this works from the 5.77.0 table split. On 29 Oct the indexes were bigger than the data on two tables: `dynadot_rows` had a 80 MB heap and 124 MB of indexes, `datasave_pool` 30 MB and 55 MB.
  - Dropped `dynadot_rows_domain_lookup` (by name alone). No query uses it: every read of `dynadot_rows` names the day and the kind.
  - `datasave_pool` fillfactor 70. `scorePool` rewrites each closeout row daily, and with room left on the page that rewrite no longer adds a primary-key entry. The pool keeps only 2–3 days, so all its pages turn over within days.
  - Rebuilt the indexes of `datasave_pool`, `dynadot_rows` and `market_names` (`REINDEX`, each file one transaction; the extra space during a rebuild is only the new indexes).
- **Expected:** roughly 80–120 MB freed, bringing the database from 74% to about 63–66%. The real figure will be in `/health.db_size` right after the deploy.
- **Not done yet:** `market_names`' heap (232 MB) is about twice its live rows, because each daily fold writes a new version of nearly every row. The 5.77.0 vacuum keeps it at that size rather than growing. Halving it needs the daily-changing fields moved to a narrow table, which DOM builds only if `/health` shows it still growing.
- **How to test it (Gavriel):** `GET /health` `db_size.percent` and `tables` after the deploy. Bulk loads pass again once the database is under 70%, and the next datasave's `engineFeed` then backfills 29 Oct.
- **Deploy:** tag → Mac host. The migrations run at start and lock these three tables for a few seconds each. Pushed outside a datasave run and the 23:45–01:00 UTC window.
- **Lessons:** size by table alone hid that indexes, not data, were the growth. Splitting heap and index (5.77.0) found it in one reading.
