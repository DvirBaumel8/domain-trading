# Release v5.26.0 (21 Oct 2026)

**Contract:** 5.26.0. CR-072 ranked closeout and drop candidates. MINOR (additive). Migration `1765800000000_v5-26-0.sql`.

## What changed (contract)
- **`GET /candidates/closeouts?date=&source=dynadot|godaddy|all|drops&max_price=&limit=`** (READ or bots; read-only, there is no POST). Returns the day's closeout rows (the GoDaddy pool and the sealed Dynadot closeouts upload) or the kept drop-list names, minus eight hard filters, ranked by the active scoring model. `limit` 1..200 (default 50; `limit=500` is 400 `VALIDATION_ERROR`). **`max_price` is USD** like every other money input (`40`, `15`, `10.50`; at most $40, default 40); the answer echoes `max_price_cents`. Default `date` = the newest day with a sealed snapshot for the source.
- **Rows:** `{domain, source, price_cents, price ("$10.88"), ends_at, score, rank, filters_passed: true, words}`; sorted by `score` descending (a `null` score last), ties by lower price, then name. `words` is the selection split of the name.
- **Summary:** `{pool_n, filtered_by: {CODE: n}, ranked_n, returned_n, snapshot_sha256}` with `pool_n - sum(filtered_by) = ranked_n`. `snapshot_sha256` equals the `sha256` of `GET /snapshots` for that day (a map `{godaddy, dynadot}` for `source=all`; `null` for `drops`). `filtered_by` always has all eight keys.
- **Filter codes** (the first failing one counts, in this order): `SPELL-1` (the `form` check fails), `BRAND-1` (brand list), `BIGCO-1` (bigco list or `bigco_names`), `TM_KILL` (`tm_kills`), `FORBIDDEN_TERM` (`/company/forbidden-terms`), `DIGITS_OR_HYPHEN` (setting, default on), `OWNED` (in the portfolio), `SALES_GRADED` (a reported sale in `engine_sales` or a sold market episode).
- **A score that failed is `score: null` with `score_reason`**, never 0: `NO_ACTIVE_MODEL`, `SCORE_FAILED`, `NOT_SCORED_YET` (listed after every scored row).
- **New code `SNAPSHOT_MISSING` (409):** no sealed snapshot for that date and source. It is not an empty list. `source=dynadot` is 409 on every day without a sealed Dynadot closeouts upload (the bots' `POST /snapshots/dynadot` with `kind: "closeouts"` and `final: true`).
- **New `datasave` step `scorePool`** (after the Dynadot steps): filters and scores the pool rows once a day, offline (no registry ask, no outside call), and stores filter code, score and model version with the rows. Dynadot closeouts rows are scored once their upload is sealed, by the next datasave run (the 60-minute retry run or the next day), so seal the upload before 15:00 UTC to be ranked the same day. The route only reads. Measured locally on 125,000 synthetic rows: about 4 seconds for the whole step.
- `source=drops`: the kept names of the drop list of the date are filtered and scored when you read them (the list is small); no price, no snapshot.
- No change to `POST /score`, `/buy`, `/portfolio/import` or any existing answer. Buying stays with Dvir's approval.

## Impact on Buyer and Gavriel
- Buyer can read the top 50 ranked closeout names with one call, and cite the pool with `summary.snapshot_sha256` and `pool_n`, instead of filtering thousands of rows in context. The route does not decide anything: Tier A judgment, picking and pricing stay with Buyer.
- Load `tm_kills` and `bigco_names` (`POST /data/tm-kills`, `/data/bigco-names`) and report sales (`POST /engine/sales`, `POST /data/sales`) so `TM_KILL`, `BIGCO-1` and `SALES_GRADED` have data to filter with; with empty tables they filter nothing.
- Until a trained model exists every row has `score: null, score_reason: NO_ACTIVE_MODEL`; the first datasave run after a model exists scores them.
- Nothing here asks Dvir to do anything.

## How to test (read only, no `dry_run` needed)
- `GET /candidates/closeouts?limit=5`: the newest sealed day, at most 5 rows, `score` descending, `price` as a dollar string. Check `summary.pool_n - sum(filtered_by) == ranked_n` and `snapshot_sha256` against `GET /snapshots?date=<date>`.
- `GET /candidates/closeouts?source=dynadot`: 409 `SNAPSHOT_MISSING` until a Dynadot closeouts upload for a day is sealed.
- `GET /candidates/closeouts?limit=500`: 400 `VALIDATION_ERROR`. `POST /candidates/closeouts` with a bots token: 403.
- `GET /candidates/closeouts?source=drops`: the kept names of the newest drop list with their scores.
- After a datasave run, `GET /jobs/runs?job=datasave` shows the `scorePool` summary (`rows_processed_n`, `rows_filtered_n`, `rows_scored_n`, `filtered_by`, `elapsed_ms`).
- Local tests: CC526-1..13 (`tests/modules/ops/closeouts.test.ts`). The admin-cli migration count is 61.

Deploy: pushed to `main` with the tag; the Mac host deploys after CI passes. Gavriel confirms the live version on `/health`.

**Lessons:** a "how long does scoring take" question is cheaper to answer by measuring on a synthetic 125,000-row pool than by guessing (the whole step takes seconds, so no row needs to be skipped for time); and a hand-written random generator in a throwaway benchmark must avoid float overflow (a first attempt looped forever on a degenerate sequence), so use the repo's seeded `makeRng`.
