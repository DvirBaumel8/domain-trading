# Release v5.4.0 (14 Oct 2026)

**Contract:** 5.4.0. CR-056 part 1: engine data (POST /engine/sales, /engine/unsold, GET /engine/health, daily engineEndings RDAP fill)

- **What changed:** the data side of the scoring engine (CR-056 part 1). `POST /engine/sales` and `POST /engine/unsold` store your sold and unsold names; `GET /engine/health` shows counts, ages, the last uploads and the progress of the endings fill; the daily job gets a new last step, `engineEndings`, which asks the registries (RDAP only, no DNS) whether each uploaded name exists on .net, .co, .org, .io and .ai, and since when. Contract: `endpoints.md` Scoring engine data, `jobs.md`. No change to `/buy`, selection, listing or scoring. The model, `POST /score` and training are the next releases (5.5.0, then health and drift in 5.6.0).
- **Impact on Gavriel:**
  - **First uploads:** send the 12,474 sales and the 19,940 unsold rows now. Up to 20,000 rows fit in one call (8 MB body limit), but chunks of 5,000 to 10,000 are safer: sales in 2 calls, unsold in 2 to 4. Writes are limited to 10 a minute per token, so there is room for a retry. Use a fresh `Idempotency-Key` per chunk and reuse it only to retry the same chunk.
  - **Rows are judged one by one.** A bad row is rejected with a reason in `rejects` (the first 200) and the rest are stored. Only second-level `.com` names are stored; the 8,405 .com sales are in, the other ~4,000 rows come back as `TLD_NOT_SUPPORTED` (send only the .com rows to keep the answers short). The word-shape regime filter happens at training, so names with digits or hyphens are stored.
  - **Duplicates:** a sale of a name within 20 days of a stored sale of the same name is a duplicate; an unsold name is a duplicate with the same name and observation date. Re-sending a file is therefore safe: everything stored comes back as `duplicate_n`.
  - **Cadence:** sales weekly (Monday), unsold daily (a random 1,000 of the day's deleted list, with its `list_date` as `observation_date`; `caught_by_catcher` from the drop watch when you know it).
  - **The endings fill takes a day or more.** From the first night after the upload, `engineEndings` asks up to 20,000 (name, ending) pairs in about 20 minutes; 32,000 names x 5 endings is about 160,000 asks, so expect about 8 nights, with `endings.pending_n` in `GET /engine/health` counting down. It is the last step of the daily run and does not delay the other steps. A run can also be started with `POST /jobs/run` (daily). Names uploaded later join the queue automatically.
  - `GET /engine/health` has no model fields yet: `model_version` is null.
- **How to test it:** (WRITE token for the POSTs)
  1. `GET /engine/health`: all counts 0, `last_upload` null.
  2. `POST /engine/sales` with two rows for one name 10 days apart, one row with `sale_date` in the future, one `.net` name: 201 with `accepted_n: 1`, `duplicate_n: 1`, `rejected_n: 2` and the reasons `DATE_IN_FUTURE` and `TLD_NOT_SUPPORTED`.
  3. `POST /engine/unsold` with two rows of the same name and `observation_date` and a bad `type`: `accepted_n: 1`, `duplicate_n: 1`, `rejected_n: 1` (`TYPE_INVALID`).
  4. Repeat step 2 with the same `Idempotency-Key`: the same answer, header `Idempotent-Replayed: true`, nothing stored again. A READ token on a POST gives 403; no token 401; `{"rows": []}` gives 422.
  5. `GET /engine/health`: `sales_n`, `unsold_n`, `sales_newest`, `data_age_days`, `last_upload` match; `endings.names_n` counts the distinct names and `pending_n` is 5 per name until the daily run has passed.
  6. After the next daily run: `GET /jobs/runs` shows the `engineEndings` step with its summary; `endings.checked_n` has grown by `asked` minus `unknown`.
- **Deploy:** one migration, `1763800000000_v5-4-0.sql` (new tables `engine_uploads`, `engine_sales`, `engine_unsold`, `engine_endings`; runs on start). Push to `main`, tag `v5.4.0`; Gavriel confirms the live version on `/health`. The new tables are not in the nightly export (it is off) and the retention job does not touch them.
