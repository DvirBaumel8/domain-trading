# Release v5.42.0 (25 Oct 2026): bulk work everywhere

**Contract:** 5.42.0. PATCH-level behaviour (no response shape, route or code changes); released as MINOR with the rest of the day. No migration.

## What changed (no response shape changes)
Production runs on the Mac and each Neon round trip costs about 1 s, so every place that worked row by row now works in bulk (gaps G-121, G-122, G-124).

| Place | Change | Queries before, after (from the tests) |
|---|---|---|
| `POST /data/sales` (5,000 rows) | stored keys read with `unnest` (5,000 a statement), inserts 1,000 a statement; same lock, transaction, 409 rule, response | 10,003 to 9 (re-post: 4) (BK542-1) |
| T30 labels (60 names) | RDAP cache read once, labels and cache answers written in batches | 183 to 7 (BK542-2) |
| Disappearance tags (100 lookups) | cache read once, first lookup alone, then 4 at a time through the Verisign host pacer, updates in batches of 300; cap exact | 313 to 13 (BK542-3) |
| Candidate intake (30 names) | decided in memory, prefetch, multi-row insert; `TOPIC_REUSED` still reads only earlier rows; on-demand re-screen and `candidate_screenings` in bulk | 90 to 8 (BK542-4) |
| `ext_dates`, `same_name`, pre-bid endings | the endings of a name are asked side by side; RDAP hosts keep their pacers; page fetches stay on the one site pacer; the IANA base is read once per run | wall time (BK542-5, BK542-9) |
| Sibling scan | see below | wall time (BK542-6) |
| Test-set seal, `POST /selection/labelled-names`, `POST /ledger/costs` | multi-row inserts (500 / 500 / 1,000); the unique violation still answers 409 `LABELLED_NAME_CONFLICT` | 502 to 3 for 500 cost rows (BK542-7) |
| `engineEndings` (600 answers) | `EndingsWriter`: flush every 500, same keep / update / append rule as v5.14.0 (compared with `saveAnswer` in the test); owned pairs stay one by one | 700 to 3 (BK542-8) |

## Impact on Gavriel
None in what to send. The sibling scan is faster: a name's siblings are checked 4 at a time, with page fetches at least `same_name.min_ms_between_fetches` (1 s) apart per host (robots.txt honoured) and at most 4 in flight. So far more names of a 20-name call finish inside the budget.
- `siblings.time_budget_seconds` (default 80 s) stays the budget of the whole call, now capped at 90 s. The API is reached through Cloudflare, which ends a request after about 100 s (HTTP 524); the builder's first draft let a call run 300 s, which would have been cut off. Names left `complete: false` are scanned again in a second call (cached answers make it quick).

## Test changes
No existing assertion was weakened. New tests BK542-1..9 (`tests/modules/bulk/`, `pickproof/pickproof`, `ops/disappearances`, `candidates/intake`, `selection/screening-registry`, `selection/sibling-scan`, `ops/auction-plans`). Query counts are asserted with `withDbScope` (v5.40.0 counter).

## How to test (via the API)
Gavriel (read only): after the deploy, `GET /selection/sibling-scan/{domain}` for a name scanned in a 20-name `POST`, more names `complete: true` than before; the daily run's step summaries (`GET /jobs/runs`) carry `db.queries`, which should drop for `engineEndings`, `buildPanel` (tags), `pickproofLabels`.


**Lessons:** a time limit must be checked against every layer a request passes through: the builder's per-name budget let a sibling scan run 300 s behind Cloudflare's ~100 s cut-off (DOM restored the whole-call budget, capped at 90 s). Measuring query counts in tests (v5.40.0 counter) made each batching gain provable: 5,000 sales rows went from 10,003 queries to 9. Builder note: the first draft of the tag loop with 4 workers made a 429 on the first lookup still send 3 more; the first live lookup now runs alone (BG052-5 keeps `lookups_n: 1`).
