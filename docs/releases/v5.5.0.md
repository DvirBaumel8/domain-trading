# Release v5.5.0 (14 Oct 2026)

**Contract:** 5.5.0. CR-056 part 2: engine model (features, GBM + logistic + price tier, POST /engine/train, weekly retrain, POST /score)

- **What changed:** the model side of the scoring engine (CR-056 part 2). `POST /engine/train` trains the score from the data you uploaded in 5.4.0 and `GET /engine/train/{id}` shows the result; `POST /score` scores up to 500 `.com` names with the newest model and answers in the shape of the request (score, percentiles against dropped and sold names, price tier, reasons, likely buyers, features). `GET /engine/health` now shows the model (version, train rows, test numbers). The daily run gets a last step, `engineTrain`, that retrains by itself. The endings fill also asks each name's own `.com` at Verisign (its registry creation date separates hand-registered names from aftermarket ones). Contract: `endpoints.md` §Scoring engine, `jobs.md`, README §Idempotency. No change to `/buy`, selection, listing or pricing.
- **Impact on Gavriel:**
  - **Train after uploading.** The model follows your uploads by itself: with no model yet, the first daily run after data exists trains one (the endings fill is the step before, so the first model is better after a few nights; train by hand with `POST /engine/train` any time, at most once a day, 409 `TRAIN_TOO_SOON` with `next_allowed_at` otherwise). After that a sales upload retrains on Monday (Israel), or when the model is 7 days old. A training takes minutes; poll `GET /engine/train/{id}` until `status` is `done` (or `failed` with the reason in `error`, for example `NOT_ENOUGH_DATA`).
  - **How to call `POST /score`.** READ token, body `{"domains": ["septicdrone.com", ...], "as_of": "2026-10-14"?}`, 1 to 500 names. It is **the one read-only POST**: no `Idempotency-Key` header and no audit row (it only caches public registry answers). 409 `MODEL_NOT_READY` until the first training is done. Endings with no stored answer are asked live (RDAP only) inside a 4-second budget; an answer that does not arrive in time is `null` in `features` and absent from `likely_buyers`, never guessed. Ask again later.
  - **The score is information only** until Dvir activates a gate (phase 2: a settings draft with his own line). Nothing in the service uses it to block or approve anything. Read `score` as a rank (it is not a chance of selling: the training mix is not the real base rate); the percentiles place it among the dropped and the sold names of the frozen test file.
  - **Word frequency is a proxy.** `zipf_min/mean/max` come from the split table's piece costs (derived from SCOWL size levels) on a 0 to 8 scale, not from `wordfreq`: no new outside data. Say so if the prototype's numbers differ.
  - **Left out on purpose:** features with no data (for example `demand` until a keyword export is uploaded, `tok_rate_pit` until the unsold rows span 90 days) and the `.com` creation date features while that date is known for under 30% of the unsold rows (a dropped name has no registry record, so it would reveal the label). They are listed in `feature_list.excluded` with the reason; the model never uses them until the data supports them. `acq` and the other values are still shown in `features` of a score.
  - **Bars:** 3 and 6 are outcomes: read `test.auc`, `auc95`, `p_top1` (with `p_top1_ci95`) and `p_top1_at_1pct_base` in `GET /engine/health`; the bars report and the ablation without the endings (bar 4) arrive in 5.6.0.
  - The endings fill now has six pairs per name (the five endings and `.com`): `pending_n` grows by one pair per name already filled. `.com` and `.net` share Verisign's pacing (4 asks a second), so for 32,000 names the first full fill takes about 13 nights instead of about 7; the model trains meanwhile, with the endings it has (unanswered = missing, not 0).
- **How to test it:** (a READ token for the GETs and `/score`, a WRITE token for `POST /engine/train`)
  1. `POST /score` with `{"domains":["septicdrone.com"]}` before any training: 409 `MODEL_NOT_READY`.
  2. After the 5.4.0 uploads: `POST /engine/train` with an `Idempotency-Key`: 202 `{train_id, status: "running", poll}`. Poll `GET /engine/train/{train_id}` until `done`; check `test_sha256`, `metrics.test.auc` with `auc95`, `metrics.weighting` (both AUCs and the choice), `feature_list`. A second `POST /engine/train` within 24 hours: 409 `TRAIN_TOO_SOON`.
  3. `GET /engine/health`: `model_version`, `trained_at`, `train_rows`, `test`, `chosen_weighting` are filled.
  4. `POST /score` with your 20 fixed names (**bar 5**): no `Idempotency-Key`; twice gives byte-identical output; time the call (stored answers: well under a second; names without stored answers add up to 4 seconds of live asks). Try a name with a digit: `in_regime: false` and a `warning`. Try an old `as_of` (for example `2025-01-01`): `*_pit` features and `likely_buyers` only show endings registered before that day.
  5. After the next daily run: `GET /jobs/runs` shows `engineEndings` (now with `com`) and `engineTrain` (`skipped` with its reason, or `started` with a `train_id`), and a `train` run when it started one.
- **Deploy:** one migration, `1763900000000_v5-5-0.sql` (table `engine_models`; `engine_endings` accepts `com`; the queue accepts job `train`; runs on start). Push to `main`, tag `v5.5.0`; Gavriel confirms the live version on `/health`. `engine_models` is not in the nightly export (it is off) and the retention job does not touch it. Training runs inside the API process (it yields to requests after every tree), so on the Mac host avoid a restart while a training runs; a restart marks it failed after 45 minutes and the next daily step retrains.
