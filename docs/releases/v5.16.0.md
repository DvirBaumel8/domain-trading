# Release v5.16.0 (18 Oct 2026)

**Contract:** 5.16.0. Ledger CSV formula guard and a test clock guard, from the first improvement loop (`docs/internal/loop/2026-10-18.md`).

**Deploy status:** pushed and tagged. The Mac host is paused on Dvir's request (18 Oct 2026), so this release goes live when the server is resumed; Gavriel confirms the version on `/health` then.

## Contract changes
`GET /ledger?format=csv` protects the text columns against spreadsheet formula injection (loop 2026-10-18 #4, G-98). A free-text cell that begins with `=`, `+`, `-`, `@`, a tab or a carriage return is written with a leading apostrophe (`'=SUM(A1)`); Excel, Numbers and Google Sheets then show the cell as plain text. Only `type`, `domain`, `deal_id`, `counterparty`, `receipt_ref` and `note` are touched. `amount_usd` stays a plain signed number. `GET /ledger` JSON, the Afternic and Sedo exports and every other route are unchanged. Documented in `docs/contract/formats.md` (Ledger CSV). The nightly `backup/ledger.csv` is built from the same rows, so it carries the apostrophes too (the restore reads the JSON table files, not this CSV).

## Impact on Gavriel and Gizbar
Nothing breaks: header, columns and amounts are as before. Gizbar (CFO bot) reading the CSV will see a leading `'` on a note or reference that used to start with `=`, `+`, `-` or `@`; strip one leading apostrophe when comparing text, or read the JSON form, which is unchanged. Normal notes, references and counterparties are not affected.

## How to test
Use a READ token on `GET /ledger?format=csv`. If a ledger row's note begins with one of the characters above (for example a note written as `-refund pending`), the CSV cell shows `'-refund pending`; the same row in `GET /ledger` JSON shows `-refund pending`. Amounts such as `-11.08` appear without an apostrophe. Local tests: L516-1.

## Internal
Test-only: guard test L516-2 (`tests/unit/test-clock-guard.test.ts`, G-111) fails when a test builds `approval_ref.approved_at` from the real clock next to a fixed-date app clock, or uses a fixed `approved_at` date with no fixed app clock (the BUG-042 pattern). It also fixed one such mix in `tests/modules/listing/list.test.ts`. No behaviour change.

**Lessons:** BUG-042 came from a test that mixed a fixed app clock with the real clock and went red with no code change; the cheapest durable guard was a scan test with a short allow-list, not a shifted-clock CI step. A CSV that humans open in a spreadsheet needs a formula guard from the first release; check every other CSV or text export we add for the same.
