# Release v5.14.0 (17 Oct 2026)

**Contract:** 5.14.0. Tech-debt pass R3: the database grows more slowly and the heavy reads do less work. No route or field changed.

- **What changed:** (A) `GET /audit` shows `"[N items, sha256:<hex>]"` for any request array of more than 50 items (drop lists, test sets, labelled names, intake lists), not the whole array. (B) The daily `retention` step also removes old drop-list data (list more than 90 days old), daily candidate lists (90 days), NameBio call counters (30 days) and superseded listing-sync rows (180 days), with six more keys in its `tables` summary. (C) The ending checks of `engineEndings` update the row in place when the answer did not change (`updated` instead of `inserted`); older identical rows were deleted by the migration. (D) The 409 `DB_SIZE_HIGH` `payload_bytes` is the body size. (E) Faster, same answers: `/report`, `/portfolio/{domain}`, `/buy` and its dry run, the screening run CSV, `/selection/buy-hold`, `/health`, the daily list build, screening runs, training and `/score`, the Afternic confirm. (F) The migration adds the indexes behind that and a delete carve-out for the five newly pruned tables. Contract: `endpoints.md` (`GET /audit`, size guard), `jobs.md` (retention, endings), `README.md` (append-only note), `test-evidence.md`.
- **Impact on Gavriel:**
  - **`GET /audit`.** A list of more than 50 items you posted is not in `request` any more; match the call by its `sha256` of the array's JSON, or by the uploaded data itself (drop lists, test sets and the like are stored in their own tables).
  - **Retention.** The step summary has more table keys; an old drop list (more than 90 days) is gone from the database, though the service already ignored it after 60 days. Nothing the buy, list or sell path reads is removed.
  - **Endings.** A re-checked ending that has not changed keeps its row (newer `checked_at`); `GET /engine/health` and `GET /owned/{domain}/endings` read the same values.
  - **Nothing else to change.** Answers have the same shape and values; `/report` and `/portfolio/{domain}` should answer faster.
- **How to test it:**
  1. `POST /candidates/drop-lists` (or any call with a list of 51 or more items) with `dry_run: true` where offered, then `GET /audit?limit=5`: the row's `request` shows `"[51 items, sha256:..."` for the list.
  2. `GET /report` and `GET /portfolio/{domain}` before and after: same fields and numbers.
  3. Read the next daily run's `retention` step in `GET /jobs/runs`: `tables` lists `drop_list_checks`, `drop_list_rows`, `drop_lists`, `daily_candidate_lists`, `namebio_calls`, `listing_sync_log`.
  4. `GET /selection/buy-hold` and `POST /buy` with `dry_run: true`: the same `would_be_blocked` and `screening_pack` fields.
- **Deploy:** migration `1764700000000_v5-14-0.sql` runs on start (a few indexes and a one-off delete; seconds at this size). Push to `main`, tag `v5.14.0`; deploys to the Mac host after CI passes (`scripts/local-host/deploy.sh`, DOM). Not during the nightly run (23:45 to 01:00 UTC). Gavriel confirms the live version on `/health`.

**Lessons:** a join key that is only checked in a subquery (`input @> ...` on a jsonb column) hides a full scan until the table grows; an index on the real lookup path costs less than the code that works around it. Collapsing "same answer again" rows at write time keeps history meaningful (a change is a row) and keeps a refresh job from growing a table forever.
