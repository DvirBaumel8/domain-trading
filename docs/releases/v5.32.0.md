# Release v5.32.0 (21 Oct 2026)

**Contract:** 5.32.0. BUG-051: /snapshots/dynadot limits documented, ROWS_LIMIT and PRICE_CAP codes. MINOR (additive). No migration.

## What changed (contract)
- `POST /snapshots/dynadot` now states its two limits: **at most 50,000 rows per call** and **every price field at most 2,000,000,000 cents** (about $20M; the cap itself is accepted).
- Each limit has its own 422 code instead of `VALIDATION_ERROR`:
  - **`ROWS_LIMIT`** `details: {max_rows: 50000, received_n}`;
  - **`PRICE_CAP`** `details: {max_cents: 2000000000, rows: [row indexes, up to 20], over_n}`.
  The row limit is checked first. Either way the whole call is refused and nothing is stored, as before. Prices are never clamped (BUG-051 Q1: refuse, the default). Every other problem stays `VALIDATION_ERROR`.
- `GET /openapi.json` already carried `maxItems: 50000` and `maximum: 2000000000`; a test now pins both.

## Impact
- **Bots uploading Dynadot rows:** split an upload above 50,000 rows into several calls with the same `kind` and `data_date`; on `PRICE_CAP`, drop the listed rows and send again. A script can branch on the code.
- Nothing here asks Dvir to do anything.

## How to test (via the API)
- 50,000 valid aftermarket rows with `dry_run: true`: 201, `received_n: 50000`. 50,001 rows: 422 `ROWS_LIMIT`.
- One row with `price_cents: 2000000001` (`dry_run: true`): 422 `PRICE_CAP` with its index. With `2000000000`: 201.
- Local test: DS532-1 (`tests/modules/ops/datasave-dynadot.test.ts`).

Deploy: pushed to `main` with the tag; the Mac host deploys after CI passes. Gavriel confirms the live version on `/health`.

**Lessons:** a limit that a bot hits in production needs its own error code and a line in the contract; "up to N per call" said in passing was not enough for a script to act on.
