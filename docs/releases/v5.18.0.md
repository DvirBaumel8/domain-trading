## v5.18.0: the $0 visitor counter (CR-068)

Contract 5.18.0 (MINOR). Dvir wants to know whether anyone visits the listed names; Afternic's dashboard shows nothing for names that are not on its nameservers. This release counts visits at no cost, with counts only.

### How it works
1. A name's Porkbun URL forward points at the counting redirect `GET /r/{domain}` on the api-proxy Worker (the stable public URL).
2. The Worker answers 302 to the same Afternic page the forward used before (no cookie, nothing cached), and only afterwards sends one count to `POST /visits/hit` with a `visits` token (3 s timeout; if the Mac host or tunnel is down the visitor is still redirected and the count is dropped).
3. The service adds to a daily row per name: `human_hits`, `bot_hits`, `capped` (past 1,000 counted hits a day) and referrer hosts (first 10 per day, the rest `other`). Nothing else is received or kept: no IP, cookie, path, query or user agent. Rows are deleted after 400 days.
4. `GET /visits/weekly?week_ending=<Saturday>` gives the Saturday digest numbers. Names on Afternic nameservers cannot be counted; they appear under `not_countable` (`afternic_ns`) with their newest imported Afternic Views/Leads, and so do listed names whose forward is not set yet (`not_forwarded`).

### Contract changes
- New scope `visits` (only `POST /visits/hit`; no other scope may call it).
- New routes: `POST /visits/hit`, `POST /visits/import`, `POST /visits/settings`, `POST /visits/forward/{domain}`, `GET /visits`, `GET /visits/weekly`.
- New codes: `VISITS_DISABLED` (409), `DOMAIN_NOT_LISTED` (422), `FORWARD_NOT_ALLOWED` (422), `PUBLIC_BASE_URL_UNSET` (422).
- `POST /visits/hit` is not written to `audit_log` per hit (the daily row is the record); every other `/visits` write is audited. It still needs an `Idempotency-Key`.

### Impact on Gavriel and the other bots
- Gavriel (WRITE): `POST /visits/forward/{domain}`, `POST /visits/settings`, and optionally `POST /visits/import`.
- Data Engineer (data): `POST /visits/import` with CR-037's Afternic Views/Leads rows `{domain, date, views_30d, leads_30d}` (a re-import of the same name and date replaces the row).
- Sales (READ): `GET /visits/weekly` every Saturday. Nobody else is affected; existing routes are unchanged.

### How to test (READ / WRITE only, no live action)
- With visits off (the default): `GET /visits` returns `enabled: false` and no rows; `GET /visits/weekly?week_ending=2026-10-17` lists every listed name under `not_countable`; `POST /visits/forward/{domain}` with `dry_run: true` and an `approval_ref` naming the domain and "visits" returns the plan (`before`, `after`) and changes nothing. `POST /visits/hit` is a visits-token route: a READ or WRITE token gets 403, and a visits token gets 409 `VISITS_DISABLED` until the counter is switched on.
- A `week_ending` that is not a Saturday is 422 `VALIDATION_ERROR`.

### What needs Dvir (each by his own line, through Gavriel)

The Mac host then creates the token, puts it into the GitHub secret `VISIT_COUNTER_TOKEN` and starts `deploy-api-proxy`, which sets it on the Worker, within about 10 minutes. Nobody sees the token. One-time: Dvir re-runs `scripts/local-host/install.sh` so the host copies the new `visits-token.sh` (and `gh` must stay signed in with rights to set secrets and run workflows; the repo secrets `CLOUDFLARE_API_TOKEN` and `CLOUDFLARE_ACCOUNT_ID` already exist). ### Deploy status

**Lessons:** the first design (a separate Worker with its own zones and nameserver moves) was replaced the same day by a URL forward plus a route on the existing api-proxy Worker: ask what already exists before adding an edge component. Review the rate limit of any new machine-to-machine token early (the general 10 a minute would have dropped most hits). The module-boundary, route-table and backup-coverage guards caught three doc and test registrations the first time; list them in the code map "where do I change X" row.
