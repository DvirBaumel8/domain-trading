# Release v5.1.0 (14 Oct 2026)

**Contract:** 5.1.0. G-95: daily data retention (old unbought screening data, old job logs and checks; tighter when the database nears the free-plan limit)

- **What changed:** a new daily step `retention` (after `postsRefresh`, before `backupExport`) deletes old data in batches of 5,000 rows, within about 60 seconds a night. It is age and size aware: normal ages below, **tight (half the age)** when the database is at or over 70% of the 0.5 GB Neon free limit (the `DB_SIZE_HIGH` threshold). No route, field or error code changes. Dvir, 14 Oct 2026: "G-95: Yes, setup a smart retention ability (cron job deletes big old data)."
- **Impact on Gavriel:** what disappears, and after how long (normal / tight):
  - screening results of names that are not in `domains`, have no screening pack and are in no test set, cohort, holdout or backtest run: 180 / 90 days. The newest result per name and check always stays, so a name you screened recently still shows its latest checks;
  - screening evidence (`GET /screening/evidence/{id}`) that no remaining result, sibling scan or registry lookup points to: 180 / 90 days (that route then answers 404 for it);
  - finished screening runs left with no results: 180 / 90 days (`GET /screening/runs/{id}` answers 404 for them);
  - sibling scans and registrar-state checks: all but the newest per name, after 90 / 45 days;
  - quotes: after 180 / 90 days, except a quote a purchase names and the newest check of each name;
  - `GET /jobs/runs` history: runs older than 60 / 30 days.
  - **Never deleted:** screening packs (and everything a pack's run holds), bought and listed names and their screening data, `audit_log`, `ledger_entries`, `sales`, `offers`, `listing_history`, pricing data, verdicts, manual quotes, test sets, cohorts, holdout and replay data, labelled names.
- **New warning `DAILY_JOB_MISSED`** in `GET /report` (warn): no scheduled daily run started in the last 26 hours, so a silent cron shows up. Manual runs do not count. Details `last_scheduled_at`, `hours_since`.
- **How to test it:** after the nightly run, read `GET /jobs/runs`: the `daily` run has a `retention` step whose summary shows `mode`, `db_bytes_before`, `db_bytes_after`, `partial` and, per table, `deleted`. Nothing needs to be called. Right after the deploy the first night may delete a lot; `partial: true` means the 60-second budget ran out and the next night continues. There is no dry-run route (DOM's tests use `RetentionJob.runOnce({dryRun: true})`).
- **Deploy:** one migration, `1763500000000_v5-1-0.sql` (a new trigger function; the delete is allowed only inside the retention step's own transaction). It runs on start. Push to `main`, tag `v5.1.0`; Gavriel confirms the version on `/health`.
