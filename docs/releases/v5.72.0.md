# v5.72.0 — CR-088: full hard-filter auction field

**Contract:** 5.72.0 (MINOR). **Migration:** `1768800000000_v5-72-0.sql`.

## What changed

The datasave `auctionShortlist` step now stores **every** GoDaddy live auction that passes the existing hard filters for that day (typically 500–750 names), instead of cutting to the top `shortlist_size` = 25. `GET /auctions/shortlist` serves the full stored field with pagination (`limit` + `offset`); `total` is the count of all eligible rows for the date. Expensive steps (other-endings RDAP, automatic pre-bid) stay top-sliced for step speed; names beyond those slices appear on the route with `prebid: null` / unknown endings.

## Impact on Gavriel

- `GET /auctions/shortlist` now returns the full field. Use `limit` + `offset` to page (max limit 10,000). `total` tells you the full count.
- Old calls with `limit=25` (no offset) are backward compatible and return at most what exists.
- The `settings.shortlist_size` in the response is now 0 (= all). A nonzero value still caps.
- Names beyond the pre-bid slice appear with `prebid: null`.

## How to test (dry_run / read-only)

```
GET /auctions/shortlist?limit=100
GET /auctions/shortlist?limit=50&offset=50
```

Check that `total` >= `rows.length` and that `offset=50` returns rows with `rank > 50`.

## Lessons

The artificial cut to 25 was a carry-over from the original tip-sheet design (G-127). Discovery of 500–750 names/day is fine for Postgres with indexes; the only cost is the extra rows in `auction_shortlist` (derived, not in the backup, pruned by retention). The rule "scale with batches/indexes/retention, not by shrinking the pool" is now documented as a company standing rule.
