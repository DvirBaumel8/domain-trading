# Release v5.21.0 (20 Oct 2026)

**Contract:** 5.21.0 (MINOR). CR-071 daily data save job (GoDaddy inventory), snapshots, datasave health

**Deploy status:** pushed and tagged; the Mac host deploys after CI passes. Gavriel confirms on `/health`.

## Contract changes
- **New job `datasave`**, run once a day at **15:00 UTC** by a GitHub Actions schedule (`.github/workflows/datasave.yml`), or by hand with `POST /jobs/run {"job":"datasave"}` (job token or WRITE). Steps, each with its own status: `godaddyInventory`, `dynadotCloseouts`, `dynadotAftermarket`, `buildPanel`, `snapshotRetention` (`jobs.md`).
- **`godaddyInventory`** reads only GoDaddy's official inventory host (`metadata.json`, then the files in the setting `datasave.godaddy_files`): `closeout_listings`, `all_expiring_auctions`, `all_biddable_auctions`, `all_listings_ending_today`, `auctions_ending_today` (each `.json.zip`, about 177 MB together). Every file gets a manifest with size, sha256 and `Last-Modified`, and is keyed by the **source's data date** (the UTC date of its `Last-Modified`), never the run date. The raw zip is kept on the server's disk (`SNAPSHOT_DIR`, default `~/Library/Application Support/domain-trading/snapshots`) for 7 days. **Only `closeout_listings` is parsed into the database**: `.com` names up to $40 (setting `datasave.pool_max_price_cents`), not adult, price in integer cents (`"$1,250"` = 125000), kept 3 days. The other four files are fetched, hashed and kept raw only.
- **Sealed manifests.** A complete file is write-once (a database trigger refuses any change except retention clearing the raw file). A second save of a sealed day fetches nothing and the step result for each file is `code: "SNAPSHOT_SEALED"` with the stored sha256. This is a step result code, not an HTTP 409: no route writes snapshots. `RAW_EXPIRED` (410) is reserved for a future re-parse route and is not emitted; nothing re-downloads or re-parses a past day (AT-9), the job only takes what is published now.
- **Errors are not zeros.** A failed fetch is `status: "error"` with `http_status` and `rows: null` (never a complete save of 0 rows); a closeouts file that could not be parsed is `partial`, `rows: null`. Neither is sealed. After a failed `godaddyInventory` step the queue adds one retry run that starts 60 minutes later (once per data day).
- **Dynadot.** `dynadotCloseouts` and `dynadotAftermarket` report `status: "not_configured"`: no Dynadot key exists on the server and DOM cannot create one. They are stubs (TODO in `docs/internal/datasave.md`), never an error, never zero rows, and they never fail the run or `/health.datasave`.
- **`buildPanel`** compares the latest parsed closeouts day with the previous one: `gone_before_end_n` = names of the previous day whose end time is after the start (00:00 UTC) of the new data date and that are absent from the new day (plus `new_n`).
- **New routes (READ, bots too):** `GET /snapshots?date=&source=` (manifests, parsed row counts, `raw_available`, `raw_deleted_at`; never raw contents or server paths) and `GET /snapshots/missing?from=&to=` (days with no complete save of every configured file; default the last 14 days).
- **`GET /health`** adds `datasave`: `ok | overdue | partial | error`. **`/report`** adds the warning `DATASAVE_MISSED` (error for `overdue`/`error`, warn for `partial`; raised only once a save or a run exists).
- `POST /jobs/run` accepts `datasave`; `GET /jobs/runs?job=datasave` lists the runs with per-step status and `data_date` in the `godaddyInventory` summary.
- Migration `1765300000000_v5-21-0.sql`: tables `snapshot_manifests` and `datasave_pool`, the four `datasave_*` columns of `settings`, the `datasave` job kind, `job_queue_runs.not_before`. New optional env `SNAPSHOT_DIR`.

## Impact on Gavriel
- Nothing to change in your calls. From tomorrow 15:00 UTC the saves run on the server; the bot-side `run_daily.sh` data saves can stop once `GET /snapshots?date=<today>&source=godaddy_inventory` shows 5 files `complete`. Read `GET /health` field `datasave` and `GET /snapshots/missing` instead of waiting for a nudge.
- The file list is the confirmed one (`auctions_ending_today` replaces `5_letter_auctions`). To change it DOM changes the setting by migration.
- The days before the first save (Oct 15-16 and any other lost day) cannot be backfilled: the sources overwrite daily.
- Gavriel's proposal of a bot-side `POST /snapshots/dynadot` upload is **not built** in this release (the request was to keep GoDaddy only for 5.21.0 if DOM preferred); it stays open in CR-071 for a later release.
- Nothing in this release asks Dvir to do anything.

## How to test
- After the first 15:00 UTC run (or a by-hand `POST /jobs/run {"job":"datasave"}`): `GET /snapshots?date=<data date>&source=godaddy_inventory` shows 5 files with sha256, bytes, `last_modified`, `status: "complete"`; `rows` is set only on `closeout_listings.json.zip`. `GET /jobs/runs?job=datasave` shows the five steps. `GET /health` shows `datasave: "ok"`.
- A second `POST /jobs/run {"job":"datasave"}` the same day: each file reports `SNAPSHOT_SEALED` and the sha256 does not change.
- `GET /snapshots/missing` lists the days not saved.
- There is no `dry_run` for this job (it only reads the public inventory host and writes its own tables); it moves no money.

Local tests: DS521-1..DS521-19 (`tests/modules/ops/datasave.test.ts`, `tests/modules/ops/unit/datasave-stream.test.ts`), with the contract-doc, bots-scope, health, admin-cli and db-types tests updated.

**Lessons:** a job with a delayed retry needs the queue to know about time (`not_before`); the first idea of re-enqueueing from inside the failing step does not work because the open run blocks the enqueue, so the retry is queued when the run is finalized. A health flag must be defined from stored facts (manifests and the last run), not from the last attempt, or a fixed test clock hides ordering bugs. Keep a download's raw file and its parse separate so a parse failure is `partial`, never a silent zero.
