# Release v5.34.0 (22 Oct 2026)

**Contract:** 5.34.0. BUG-052: closeout disappearances tagged bought, deleted or unknown by RDAP. MINOR (additive). Migration `1766300000000_v5-34-0.sql`.

## What changed (contract)
- **Every disappearance gets an RDAP tag**, written by the datasave step `buildPanel`:
  - closeout names that left the feed before their `ends_at` (GoDaddy, and sealed Dynadot closeouts uploads);
  - market episodes labelled `DISAPPEARED`.
- **The rule:**
  - `deleted`: not registered (404), a status with redemption period or pending delete, or a registration created after the name was last seen;
  - `bought`: registered, active, at a registrar other than the one it had before it left (an RDAP answer stored before it left, else the feed's own registrar: GoDaddy, which includes Wild West Domains, or Dynadot);
  - `unknown`: everything else (same registrar, no baseline, an error, a timeout, not `.com`, not checked yet). Never a guess.
- **Retries:** `bought` and `deleted` are final. An `unknown` is checked again once a day until 7 days after its first check.
- **Limits:** at most 1,500 live lookups a run (`settings.disappearance_lookups_max_per_run`), closeouts before episodes, newest first. A 429 stops the tagging and the step stays ok. These lookups do not count against the bots' RDAP limit.
- **Backfill:** the first run tags every stored day pair (the pool keeps 3 days) and every current `DISAPPEARED` episode.
- **`buildPanel` summary** adds:
  - `gone_bought_n`, `gone_deleted_n` and `gone_unknown_n` (their sum is `gone_before_end_n`);
  - `dynadot`, the same split for the two latest sealed Dynadot closeouts uploads (null until two exist);
  - `tags`, the run summary with `eligible_n`, `lookups_n`, `retagged_n`, `bought_n`, `deleted_n`, `unknown_n`, `cap` and `stopped_reason`.
- **`GET /market/episodes`** adds `disappearance_tag` and `disappearance_tag_reason` per row (null unless the row is `DISAPPEARED`), and `summary.disappeared_by_tag`.

## Impact
- **DOM Architect, Gavriel:** read the competition numbers as `gone_bought_n` plus a share of `gone_unknown_n`, never the whole `gone_before_end_n`. Expect `bought` to be rare for closeouts: a closeout bought by a customer of the same registrar stays there (a transfer is locked for 60 days), and Verisign's `.com` RDAP shows no owner, so that sale reads `unknown`. The useful split is the `deleted` count.
- Episode tags use the episodes of the previous run (`episodes` runs after `buildPanel`), so a new `DISAPPEARED` row is tagged a day later.
- Nothing here asks Dvir to do anything.

## How to test (via the API)
- After the next datasave run: `GET /jobs/runs?job=datasave`, step `buildPanel`. Check that `gone_bought_n + gone_deleted_n + gone_unknown_n == gone_before_end_n`, and read `tags` (the first run is the backfill).
- `GET /market/episodes?rule=DISAPPEARED&limit=20`: every row has `disappearance_tag`, and `summary.disappeared_by_tag` adds up to the DISAPPEARED total.
- Local tests (AT → test): AT-1 BG052-1, AT-2 BG052-2, AT-3 BG052-3, AT-4 BG052-4, AT-5 BG052-5, AT-6 BG052-6, AT-7 BG052-7, plus BG052-8 (re-registered, no baseline, non-.com), all in `tests/modules/ops/disappearances.test.ts`.

Deploy: pushed to `main` with the tag; the Mac host deploys after CI passes (and runs the migration). Gavriel confirms the live version on `/health`.

**Lessons:** a request that reuses a shared limit can starve its other users. Check who else draws on a limit before agreeing to share it, and give an internal step its own cap.
