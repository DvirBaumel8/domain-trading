# Release v5.38.0 (25 Oct 2026)

**Contract:** 5.38.0. `GET /health` `db_size.tables`. MINOR (additive). No migration.

## Why
Improvement loop 2026-10-25, item 1 (G-119). The database grew from 87.2 MB (19 Oct) to 349.7 MB (25 Oct), about 44 MB a day. At that rate it reaches the 70% warning around 3 Nov and the 1 GB guard around 10 Nov. `/health` showed only the total, so nobody could see which table grows. DOM never queries the database directly (HARD RULE), so the split has to come through a READ route.

## What changed (contract)
- `db_size.tables`: the 10 largest public tables, largest first, `{table, bytes, rows_estimate}`. `bytes` = table + indexes + TOAST; `rows_estimate` = Postgres's planner estimate (null before the first analyse).

## Impact on Gavriel
- Nothing to change. Add the top three tables to your weekly loop block when you're back.
- DOM reads this field itself and plans the cut (step 2 of G-119) from it.

## How to test (via the API)
- `GET /health` with a READ token: `db_size.tables` has at most 10 rows, sorted by `bytes` descending.
- Local test: L538-1 in `tests/modules/ops/health.test.ts`.

Deploy: pushed to `main` with the tag; the Mac host deploys after CI passes. Gavriel (or DOM, read-only) confirms 5.38.0 on `/health`.

**Lessons:** a health number without its breakdown can only raise an alarm, not point at a fix. Return the parts with the total.
