# Release v5.29.0 (21 Oct 2026)

**Contract:** 5.29.0. CR-074 RDAP lookup service with cache and rolling limit; bots scope checked before the body. MINOR (additive). Migration `1766100000000_v5-29-0.sql`.

## What changed (contract)
- **`GET /rdap/{domain}`** (READ or bots): `{domain, registered: true|false|null, created, expires, registrar, status[], checked_at, cache_age_s, source: "rdap", reason_code?}` for a `.com`. A cached answer younger than 24 hours (`lookups_rdap_ttl_hours`) is served with no limit used; `?fresh=true` asks the registry and counts.
- **`POST /rdap/batch`** (READ, bots or WRITE): `{domains: [1..500], fresh?}`; rows in the same shape, in order, cached first, live for the rest while slots remain. Out of slots: the remaining rows are `registered: null, reason_code: "LOOKUP_LIMIT"`, the answer has `limit_hit: true` and `retry_after_s`. A whole 429 only if no row at all could be answered. 501 names: 400 `VALIDATION_ERROR`. It is a **read-only POST** (it writes only the cache and the usage log): no `Idempotency-Key` needed, no audit row, like `POST /score`.
- **Limit:** 200 live lookups per **rolling 24 hours** (`lookups_rdap_daily_limit`, UTC timestamps, no reset at midnight). Over it: cached still 200; a needed live lookup is 429 `LOOKUP_LIMIT` with `retry_after_s` and a `Retry-After` header. **`GET /lookups/usage`**: `{source: "rdap", used, limit, remaining, window_hours, window_start, resets_gradually: true, next_slot_at}`.
- **Errors are not zeros:** `TIMEOUT`, `SOURCE_ERROR`, `RATE_LIMITED` give `registered: null` plus `reason_code`, never `false`, and are not cached (the next call asks again; the slot is spent).
- **One cache, shared with the internal steps.** They never count against the bot limit. Fill: the screening checks, the drop-list watch, the cohort outcomes, the sibling scan and the portfolio check write every definite answer into the cache. Read: the pick-proof T30 labels read it (an answer up to 24 hours old). Not changed: the scoring engine's ending lookups (160,000 asks by design) and `/check`, `/buy` and the reconciler (they need the answer now).
- **Bots scope before the body (Gavriel's CR-076 note):** a bots token on a money route is 403 `SCOPE_FORBIDDEN` whatever the body is, including a body that is not JSON (it was 400 `INVALID_BODY` before); with `dry_run: true` the route's own validation (422) follows. A schema-invalid body already got 403 before this release on the routes checked (the venue route included); the unparseable-body gap is what changed, and a test now pins both.
- **Not built:** `GET /tm/{term}` (R-3): every official USPTO API needs a key and Dvir creates none; `POST /data/tm-kills` stays the way to load trademark kills.
- Two new settings (migration only): `lookups_rdap_ttl_hours`, `lookups_rdap_daily_limit`. Tables `rdap_cache`, `lookup_usage` are not in the backup. The admin-cli migration count is 64.

## Impact
- **Buyer, Sales, Risk Gate:** call `GET /rdap/{domain}` or `POST /rdap/batch` instead of their own RDAP fetches; repeated names within a day are free. Read `rows[].registered === null` as "unknown, try later", never as "free". Watch `limit_hit` / `retry_after_s` in a batch and `GET /lookups/usage` before a big batch; all bots share the 200.
- **Gavriel:** nothing to do. Trademark checks stay with Risk Gate on the bot side.
- Nothing here asks Dvir to do anything.

## How to test (via the API)
- `GET /rdap/google.com` twice: the second has `cache_age_s > 0`; `GET /lookups/usage` shows `used: 1`. `GET /rdap/google.com?fresh=true` raises `used` to 2.
- `POST /rdap/batch` with 501 names: 400 `VALIDATION_ERROR`. With a few names, a mix of cached and new ones: `cached_n` and `live_n` add up to the distinct names.
- `POST /buy` or `POST /list/x.com` with a bots token and a body that is not JSON: 403 `SCOPE_FORBIDDEN`; with `{"dry_run": true}` and a bad field: 422.
- Local tests: RL529-1..10 (`tests/modules/ops/rdap-lookups.test.ts`), BS529-1 (`tests/modules/http/bots-scope-order.test.ts`); `docs/internal/lookups.md`.

Deploy: pushed to `main` with the tag; the Mac host deploys after CI passes. Gavriel confirms the live version on `/health`.

**Lessons:** a limit that must not jump at midnight is a log of timestamps counted over a sliding window, not a counter with a reset time; reserving the slots inside one locked transaction before the slow call keeps it correct under concurrent callers. The CR's own acceptance case (150 + 60 with a limit of 200) is a 50-name partial batch, which is why a batch answers rows with a reason instead of failing as a whole. Check the claim in a bug note with a test before changing code: the schema-invalid case was already 403, only the unparseable body was not.
