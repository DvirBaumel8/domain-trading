# Release v5.22.0 (21 Oct 2026)

**Contract:** 5.22.0. CR-071 R-8..R-10: Dynadot bot uploads, GoDaddy auction endings. MINOR (additive). Migration `1765400000000_v5-22-0.sql`.

## What changed (contract)
- **New route `POST /snapshots/dynadot`** (bots or WRITE token, `Idempotency-Key`, audited, `dry_run` supported, 8 MB body). The server has no Dynadot key, so the bots pull Dynadot read-only and upload the rows; DOM stores and seals them like the GoDaddy files.
  - Body: `{kind: "aftermarket" | "closed_auctions" | "closeouts", data_date: "YYYY-MM-DD", rows: [...], final?: true, dry_run?: true}`. Up to 50,000 rows a call; several calls with the same `kind` and `data_date` are fine; the call with `final: true` seals the day.
  - **Exact row formats** (strict: unknown keys, strings for numbers or a decimal price are 422 `VALIDATION_ERROR` for the whole call, nothing stored; every price is **integer cents**; domains are lowercased):
    - `aftermarket`: `{"domain": "name.com", "listing_id": "12345", "price_cents": 125000}`. Rows under 50000 cents are dropped and counted (`dropped_under_500_n`, same number as `dropped_below_floor_n`). Unique by `listing_id` per day.
    - `closed_auctions`: `{"domain": "name.com", "end_time": "2026-10-19T20:00:00Z", "bid_count": 7, "final_price_cents": 123400}`. Unique by domain per day.
    - `closeouts`: `{"domain": "name.com", "price_cents": 500, "ends_at": "2026-10-21T10:00:00Z"}` (`ends_at` optional). Unique by domain per day.
  - Answer 201: `{kind, data_date, dry_run, final, sealed, status, received_n, accepted_n, duplicate_n, dropped_under_500_n, dropped_below_floor_n, rows_stored_n, sha256, audit_id}`. `data_date` may not be in the future (UTC); an empty `rows` is allowed only with `final: true` and at least one stored row.
  - **Sealing:** `final: true` makes the manifest `complete` with a sha256: SHA-256 of the UTF-8 `JSON.stringify` of the stored rows sorted by domain then `listing_id`, each row with the keys in the order above (`end_time` / `ends_at` as `YYYY-MM-DDTHH:mm:ss.sssZ`, a missing `ends_at` as `null`). Any later upload for that kind and day is **409 `SNAPSHOT_SEALED`** and changes nothing.
  - Read back: `GET /snapshots?date=D&source=dynadot_aftermarket` (also `dynadot_closed_auctions`, `dynadot_closeouts`) shows the manifest with `origin: "bot_upload"`; add `rows=100` to see stored rows.
- **GoDaddy auction endings (R-10).** The `godaddyInventory` step now also parses the four auction files. A `.com` auction that reached $500 is followed until it leaves the files; then its last bid count and price are its final state. `GET /snapshots?date=D&source=godaddy_auction_end` returns `auctions` ended on data date D with `bid_count`, `final_price_cents`, `max_price_cents`, `end_time` (0 bids = unsold, for CR-075). Nothing is stored for auctions under $500 that never reached it. Step summary: `auctions_seen_n`, `tracked_n`, `ended_today_n`.
- The four auction files now show `rows` (a number) in `GET /snapshots` instead of `null`; a parse failure makes that file `partial` with the error, never zero rows, and does not touch the closeouts or their sealing.
- `/health.datasave` and `DATASAVE_MISSED`: once a Dynadot kind has had an upload, a missing sealed upload for the due day (after 16:00 UTC; before that, yesterday's) makes the state `partial` and adds `dynadot_<kind>` and `dynadot_missing` to the warning. Before the first upload of a kind nothing changes.
- The `dynadotCloseouts` / `dynadotAftermarket` steps stay `not_configured` and add `bot_upload` (is today's upload sealed).
- Retention: uploaded `closeouts` rows 3 days; `aftermarket` and `closed_auctions` rows and ended auctions 120 days (settings `datasave.dynadot_keep_days`, `datasave.auction_keep_days`, migration only). Manifests stay.

## Impact on Gavriel
- Buyer / DOM Architect can start posting the Dynadot pulls (at most 5 Dynadot calls a day on your side) with a bots or WRITE token; the data token cannot call this route. Send `kind`, the UTC `data_date` of the pull, rows in parts if large, and `final: true` on the last call. Put an `Idempotency-Key` on every call.
- From the first day a kind is uploaded, a missing sealed upload after 16:00 UTC raises `DATASAVE_MISSED` (warn). Stay quiet until you start.
- The first auction endings appear the day after the first run of 5.22.0, for auctions that reached $500 and left the files after their end time. Nothing before the first run can be backfilled.
- Nothing here asks Dvir to do anything.

## How to test
- `POST /snapshots/dynadot` with `"dry_run": true`, a few rows and `"final": true`: the answer shows the counts and `sealed: false`; `GET /snapshots` shows nothing new.
- A real small upload for a test `data_date`, then `final: true`: `GET /snapshots?date=<D>&source=dynadot_aftermarket&rows=10` shows `status: "complete"`, `sealed: true`, the sha256 and `origin: "bot_upload"`; a second upload for the same kind and day is 409 `SNAPSHOT_SEALED` with the same sha256.
- After the next `datasave` run (15:00 UTC or `POST /jobs/run {"job":"datasave"}`): the `godaddyInventory` summary has `tracked_n`; `GET /snapshots?source=godaddy_auction_end` lists endings from the second day on.
- Local tests: DS522-1..DS522-15 (`tests/modules/ops/datasave-dynadot.test.ts`); DS521-4 and DS521-16 updated (the auction files are parsed, so they report `rows` and must be valid zips).

Deploy: pushed to `main` with the tag; the Mac host deploys after CI passes. Gavriel confirms the live version on `/health`.

**Lessons:** a route that seals a day in parts needs the seal inside the same transaction as the last rows, and `dry_run` is cheapest as the real code path rolled back (one code path, no drift). A new parser on files that used to be only hashed turns "fetched ok" into "parsed ok", so existing tests that fed junk bytes had to change: check what the fixtures assume before widening what a job parses.
